# @ama/agent-creative

Implements: docs/03-architecture/agent-framework.md (role: Creative Agent, added 2026-08-21)

Fills the gap identified when reviewing the reference conveyor: PPC/Media Buyer run campaigns, Copywriter writes the text, but nobody produced the actual visual/video material to run *with* that text. Explicit boundary against the four roles it could be confused with — see `creative-agent.ts`'s own comment: text is Copywriter's, budget/audience is Media Buyer's, campaign configuration is PPC's, product UI/UX is UI Designer/UX's. This role only produces ad creative (banners, images, short video).

- `creative-agent.ts` — `createCreativeAgent(callModel)`: calls the `creative-generation` tool first (same "tool before model" order as `@ama/agent-ui-designer`'s `design-tool`), then asks the model to explain/refine what the tool produced. Writes to **Task Memory** (`creative-assets`), same convention as PPC's `campaign-summary` — a per-Task artifact, archived into Project Memory afterward so PPC's own Task can read it.
- `dispatch.ts` — `prepareCreativeInvocation`: thin wrapper over `@ama/workflow-engine`'s `prepareAgentInvocation`, same shape as every other role's dispatch file. Accepts `projectContextKeys` (e.g. Copywriter's `<taskId>:copy-draft` and Media Buyer's `media-budget-plan`) — **same caveat as `@ama/agent-ui-designer` and `@ama/agent-analytics`**: `assemblePrompt` only surfaces *string*-valued Project Memory entries, and both of those are structured objects, so this is real wiring that doesn't yet surface as prompt text. Not re-solved here — it's a pre-existing, already-documented gap in `@ama/prompt-architecture`, not something specific to this role.

**Where it sits in the graph** (`apps/web/lib/orchestrator.ts`'s ads-task branch): `Research → Copywriter, Research → Media Buyer` (parallel) `→ Creative (depends on both) → PPC (depends on Creative + Media Buyer) → Analytics → QA → Report`. PPC no longer only depends on Research for the ads task — it now also depends on Creative, so campaign configuration happens after the creative material exists, not before.

**What's real vs. stubbed**, mirroring every other role package's own honesty about this: the `creative-generation` tool has a genuine implementation — `apps/web/lib/tools/creative-generation.ts` calls OpenAI's image API (`gpt-image-1.5` by default, overridable via `OPENAI_IMAGE_MODEL`; deliberately *not* `gpt-image-1`, which OpenAI is retiring 2026-10-23) for real when `OPENAI_API_KEY` is configured, gracefully degrading to a placeholder ref otherwise (same pattern as every `isXConfigured()` tool in that file). It does **not** persist the generated image bytes to blob storage — that's Backlog, same "container, not full pipeline" status as `datalens.ts`'s `provisionWorkbook`. What comes back is a stable content-hash ref proving the real call happened, not the image itself.

Video generation is out of scope for this first iteration (see Backlog: Sora's own API is scheduled for shutdown 2026-09-24 with no OpenAI-announced replacement, and the tool contract here is provider-abstracted specifically so a real video provider — e.g. Veo 3.1 or Kling 3 — can be added later without touching this role's contract).

`creative-agent.test.ts` tests the handler in isolation (fake ports). `integration.test.ts` runs Copywriter → Media Buyer → Creative through real `MemoryStore`/`ToolRegistry`/`CredentialStore`, checked end to end the same way `@ama/agent-ui-designer`'s integration test chains UX → UI Designer.
