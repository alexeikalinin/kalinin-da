Сейчас `google-ads.ts`/`yandex-direct.ts`/`meta-ads.ts` только читают список и создают кампании (PAUSED), без единой цифры по расходу/показам/кликам; метрики есть только со стороны аналитики (GA4/Метрика), не со стороны самого рекламного кабинета. | 19 | ~~Открытый архитектурный вопрос: чем визуализировать статистику Google Ads...~~ — **Решено, 2026-08-18**: вместо коннектора к самому Google Ads, DataLens подключён нативным PostgreSQL-коннектором к своей же таблице `ad_stat` в Supabase (уже объединяет Google Ads + Яндекс.Директ по обоим клиентским аккаунтам). Реальные находки: прямой хост Supabase (`db.<ref>.supabase.co`) отдаёт только IPv6 — нужен Session Pooler (IPv4); сертификат Supabase не проходит проверку по умолчанию — CA-сертификат надо вручную прикрепить в настройках подключения DataLens; названия сущностей DataLens не должны содержать `/` (даёт непрозрачный 400); `createDataset` может упасть 500 при автоинтроспекции источника — явно переданный `raw_schema` эту проблему обходит. См. `apps/web/lib/tools/datalens.ts` (`createPostgresConnection`, `createAdStatDataset`) и реальный дашборд «Медавеню — обзор рекламы» | Пользователь, 2026-08-15 (открыт) → закрыт 2026-08-18 | — |
| 20 | Формализовать в самом продукте (не только в процессе оператора) явный вопрос при онбординге нового клиента: есть ли у него уже свои Google Ads/Яндекс.Директ/GA4+GTM/Метрика/Meta Ads аккаунты — прежде чем создавать Project. Сейчас `real-tools.ts` молча использует sandbox-аккаунт агентства, если `ProjectInput` не передал `googleAdsCustomerId`/`gtmAccountId`/`gaAccountId`/`yandexClientLogin`/`metaAdAccountId` — это удобно для теста/демо, но для реального клиента рискует создать дубли инфраструктуры вместо подключения к уже существующей. Пока это держится на памяти оператора (см. память `feedback_client_onboarding_ask_existing_accounts`), не на самом workflow — нет ни одного агента (PM/CEO), который бы сам задавал этот вопрос при приёме нового клиента | Пользователь, 2026-08-15 — явно попросил не забывать про этот риск при работе с новыми клиентами | Когда встанет задача формализовать интерактивный intake для нового клиента (не просто сырой JSON в `POST /api/projects`) |
| 21 | Формальный агентский кабинет VK Ads (единый доступ ко всем клиентским аккаунтам, `grant_type=agency_client_credentials`) недостижим на старте — требует историю расходов от 100 000 ₽/мес за 2 месяца подряд и публичный сайт агентства с кейсами от 3 месяцев. Сейчас `vk-ads.ts` работает через обычный (не агентский) аккаунт пользователя (id `25874968`), по одной интеграции на клиента вместо единого MCC-подобного доступа, как у Google Ads | Решение пользователя, 2026-08-15 — сознательный компромисс на старте | Когда у агентства накопится история расходов и публичный сайт с кейсами, достаточные для подачи заявки на агентский статус VK Ads |
| 22 | `vk-ads.ts`'s `DEFAULT_PACKAGE_ID` (3509, `branding_universal_banner`) специфичен для аккаунта, на котором тестировали интеграцию — доступность Package в VK Ads оказалась привязана к конкретному аккаунту (большинство `site_conversions`-пакетов вернули `invalid_package` именно на этом аккаунте). Для нового клиентского VK Ads аккаунта этот package_id может не подойти — нужен способ определять подходящий Package динамически (или процесс подбора вручную на онбординге) | Решение пользователя, 2026-08-15 — обнаружено при интеграции, не решено | Когда появится второй реальный VK Ads аккаунт (клиентский, отличный от аккаунта тестирования) |
| 23 | Durable-исполнение графа (`apps/web/lib/workflows/execute-project.ts`, Vercel Workflow DevKit) проверено только под локальным dev-бэкендом ("Local World") — internal-роуты (`app/api/internal/projects/[id]/*`), через которые шаги общаются с приложением, читают/пишут тот же in-process `ProjectRecord`/`MemoryStore` (`globalThis`-синглтоны). В реальном распределённом Vercel-деплое ("Vercel World") это остаётся узким местом: сам факт, что шаги больше не предполагают общую память процесса, уже проверен и не потребует переделки, но персистентность самого приложения (что стоит за internal-роутами) всё ещё нужно перевести на Supabase (`supabase/migrations/0001_init.sql`, миграция существует, не подключена) прежде чем реальный многоинстансный деплой можно будет доверять этому пути | Решение/находка, 2026-08-17 — при подключении Workflow DevKit | Перед первым реальным деплоем на Vercel (не `next dev`) |
