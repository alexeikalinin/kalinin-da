# Glossary

Статус: Draft v0.1 — на ревью
Назначение: единый словарь терминов проекта AI Marketing Agency. Любой другой документ в `/docs` обязан использовать термины строго в значении, определённом здесь. Если термин используется иначе — сначала правится Glossary (через RFC), затем документ.

Термины сгруппированы по разделам. Внутри раздела — по алфавиту.

## 1. Общие понятия платформы

**AI Marketing Agency (платформа)**
Автономная система, выполняющая полный цикл маркетинговых задач (анализ → планирование → исполнение → контроль качества → отчёт) силами специализированных AI-агентов, с минимальным участием человека. Не путать с отдельным ботом или инструментом — это оркестрируемая система множества агентов.

**Project (Проект)**
Единица работы верхнего уровня, инициируемая пользователем: содержит входные данные (URL сайта, описание бизнеса, продукт, маркетинговую задачу) и завершается выдачей готового комплекта материалов. Проект состоит из одной или нескольких Task.

**Task (Задача)**
Единица работы, выполняемая одним Agent или последовательностью агентов в рамках Project. Имеет вход, выход, статус и критерии завершения. Task может порождать дочерние Task (декомпозиция).

**Session (Сессия)**
Один непрерывный цикл исполнения — от запуска до паузы/завершения/сбоя. В рамках одного Project может быть несколько Session (например, после Recovery начинается новая сессия для того же проекта).

**Agent (Агент)**
Независимый исполняемый модуль, реализующий одну специализацию (роль) в системе — см. раздел 2 «Роли агентов». Полная спецификация контракта агента определяется в Agent Framework.

**Role (Роль)**
Функциональная специализация, которую может исполнять Agent (например, SEO, Copywriter). Роль — это спецификация обязанностей; Agent — это исполняющий её экземпляр.

**Human-in-the-loop (Точка вмешательства человека)**
Явно определённая точка в Workflow, где выполнение приостанавливается до подтверждения человеком. Отличается от Human Review на этапе проектирования документации (см. раздел 5) — здесь речь о runtime-поведении платформы, а не о процессе написания доков.

## 2. Роли агентов (referensный конвейер)

Ниже — референсная цепочка ролей, используемая как минимальный сценарий при проектировании Agent Framework и Workflow Engine (см. Risk Register, п. «over-engineering»). Полный перечень ролей фиксируется отдельно и может расширяться без изменения архитектуры.

- **CEO Agent** — принимает Project, определяет стратегию и назначает Project Manager Agent.
- **Project Manager (PM) Agent** — декомпозирует Project на Task, планирует порядок исполнения, контролирует прогресс.
- **Research Agent** — собирает и структурирует вводные данные о бизнесе, рынке, конкурентах.
- **SEO Agent** — формирует SEO-стратегию и рекомендации.
- **PPC Agent** — проектирует рекламные кампании (paid search).
- **Media Buyer Agent** — планирует размещение и бюджет медиазакупки.
- **UX Agent** — прорабатывает пользовательские сценарии и структуру интерфейса.
- **UI Designer Agent** — создаёт визуальные макеты на основе UX.
- **Copywriter Agent** — генерирует текстовые материалы.
- **Frontend Agent** — реализует интерфейсные материалы (в рамках Этапа 2, после утверждения документации).
- **Analytics Agent** — оценивает метрики и эффективность.
- **QA Agent** — проверяет качество результатов других агентов перед выдачей.
- **Report Generator Agent** — собирает финальный комплект материалов для пользователя.

## 3. Система памяти

Многоуровневая система хранения контекста. Уровни перечислены от самого краткоживущего к самому долгоживущему. Полные правила чтения/записи/удаления — предмет отдельного документа `memory-system.md`; здесь фиксируются только границы понятий.

**Session Memory**
Контекст, актуальный только в рамках одной Session. Уничтожается по завершении сессии (если не перенесён на уровень выше явным механизмом).

**Task Memory**
Контекст, привязанный к конкретной Task: входные данные, промежуточные результаты, история действий агента в рамках этой задачи.

**Project Memory**
Контекст, накопленный в рамках одного Project и переживающий отдельные Session (используется, в частности, механизмом Recovery).

**Company Memory**
Контекст уровня организации-пользователя (клиента платформы): данные, релевантные для всех проектов одного клиента (бренд, тональность, ранее принятые решения).

**Knowledge Base (KB)**
Статические, декларативные факты о доменах, индустриях, клиентах — не зависящие от истории конкретных запусков агентов. Отличие от Learning Memory: KB не выводится из опыта исполнения, а вносится/подтверждается как факт.

**Learning Memory**
Знания, выведенные из истории исполнения (успехи, ошибки, эффективность промптов и инструментов), формируемые через Reflection. Используется для предотвращения повторения известных ошибок и повышения качества со временем.

## 4. Исполнение и координация

**Workflow**
Определённая последовательность/граф Task между агентами для конкретного типа Project.

**Workflow Engine**
Подсистема, исполняющая Workflow: запускает агентов, передаёт данные между ними, отслеживает состояние, поддерживает паузу/возобновление.

**Queue (Очередь)**
Механизм асинхронной передачи Task между агентами/подсистемами.

**Event (Событие)**
Факт, зафиксированный в системе (например, «Task завершена», «Agent вернул ошибку»), используемый для координации через Queue/Events-шину и для записи в Logging/Audit.

**Recovery**
Механизм восстановления исполнения Project после сбоя: определение последнего согласованного состояния, незавершённых Task и автоматическое продолжение без вмешательства человека.

**Reflection**
Процесс постпроектного самоанализа: оценка успешных решений, ошибок, повторяющихся проблем, эффективности промптов и инструментов. Результат Reflection пополняет Learning Memory.

**Logging / Audit**
Подсистема журналирования всех действий агентов (идентификаторы проекта/задачи/агента, время, инструменты, решения, ошибки, результат), обеспечивающая полную восстановимость истории выполнения.

## 5. Governance и процесс

**RFC (Request for Comments)**
Документ-предложение архитектурного решения до его утверждения: описывает проблему, варианты, сравнение, риски. Живёт в `/rfc`.

**ADR (Architecture Decision Record)**
Зафиксированное и утверждённое решение (после RFC). Живёт в `/adr`. В отличие от RFC — неизменяемая историческая запись; отменяется только новым ADR, не редактируется задним числом.

**Definition of Done (документа)**
Критерий готовности документа к утверждению: наличие разделов Purpose, Scope, Dependencies, Open Questions, Decision Log (вводится для снятия субъективности ревью, см. риск в предыдущем ревью директивы).

**Risk Register**
Реестр выявленных архитектурных рисков и технического долга, накапливаемый по итогам ревью документов и Reflection.

**Single Source of Truth (SSOT)**
Принцип: на Этапе 1 вся документация в `/docs` — единственный источник истины; никакое решение не считается действующим, пока не отражено в документации.

## 6. Промпты, инструменты, модели

**Prompt Architecture**
Структура, шаблоны и версионирование промптов, используемых агентами.

**Tool (Инструмент)**
Внешняя функция/API, вызываемая агентом для выполнения действия (не сам агент).

**MCP (Model Context Protocol)**
Протокол интеграции инструментов и внешних источников данных с агентами; используется как стандартный механизм Tool Integration.

**Cost Optimization**
Принцип и механизм выбора конкретной LLM для конкретной Task на основе стоимости, качества, скорости и сложности задачи — противопоставлен использованию одной самой дорогой модели для всех задач.

## Открытые вопросы (Open Questions)

Фиксируются здесь до разрешения; переносятся в Risk Register, если не будут закрыты до утверждения Architecture Overview.

1. Разграничение Knowledge Base ↔ Learning Memory зафиксировано на уровне определений (см. выше), но требует подтверждения на этапе `memory-system.md`: возможно ли для агента писать в KB напрямую, минуя Reflection?
2. Соотношение Human-in-the-loop (runtime) и RFC/ADR (design-time) — требует явного решения в Architecture Overview: применяется ли механизм RFC к решениям, принимаемым CEO Agent во время исполнения, или только к решениям людей-архитекторов на этапе проектирования.
3. Referensный конвейер ролей (раздел 2) зафиксирован как минимальный набор для первой итерации Agent Framework — требует вашего подтверждения на следующем этапе (Vision/Business Goals), не является финальным списком ролей платформы.
