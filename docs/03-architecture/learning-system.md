# Learning System

Статус: Draft v0.1 — на ревью
Назначение: описать, как накопленный опыт (Learning Memory) реально используется агентами в новых проектах — то есть как система становится "умнее" со временем, а не просто копит записи, которые никто не читает.

Простыми словами: мало просто вести дневник ошибок — важно, чтобы новый сотрудник перед началом похожей задачи заглянул в этот дневник. Learning System — это правило "кто, когда и как заглядывает" в накопленный опыт (Learning Memory, см. [[Memory-System]]), и как это опыт предотвращает повторение уже известных ошибок (прямое требование директивы).

Сам процесс "как именно формируется вывод из завершённого проекта" — это отдельный документ [[Reflection-System]] (следующий). Learning System фокусируется на том, что происходит **после** того, как вывод уже сформирован: как он хранится структурно, как находится нужный опыт под новую задачу, и как он используется.

Использует термины из [[Glossary]]. Опирается на [[Memory-System]] (раздел про Learning Memory) и [[Knowledge-Base]] (для понимания границы).

---

## Purpose

Зафиксировать механизм, которым Learning Memory реально влияет на поведение будущих агентов, чтобы Prompt Architecture и Agent Framework могли определить, как именно этот опыт попадает в контекст агента при выполнении новой Task.

## Scope

Документ описывает: структуру единицы обучения ("урок"), как система находит релевantный прошлый опыт под новую задачу, как это предотвращает повторение ошибок, и решает открытый вопрос про обмен опытом между тенантами. Не описывает: как именно проводится анализ завершённого проекта (Reflection System), не описывает алгоритмы поиска/similarity (техническая деталь Database/реализации, не архитектурное решение).

---

## 1. Единица обучения ("Урок")

Каждая запись в Learning Memory — это не просто текст, а структурированный "урок", содержащий (согласно директиве, раздел Reflection):
- что произошло (ситуация — например, "Copywriter написал текст в формальном стиле для молодёжного бренда");
- была ли это удача или проблема;
- какой вывод из этого следует ("для сегмента 18-25 разговорный стиль получает более высокую оценку QA");
- к какой роли/типу задачи это относится (например, к Copywriter Agent, к задачам про молодёжные бренды);
- насколько система уверена в этом выводе (единичный случай vs повторяющаяся закономерность — прямое требование директивы "повторяющиеся проблемы").

## 2. Как это используется новым агентом (пример на referensном сценарии)

Когда PPC Agent начинает новую Task, прежде чем действовать, он получает не только Project/Company Memory и Knowledge Base, но и релевантные "уроки" — те, что относятся к его роли и к похожей ситуации. Пример: если в прошлом Learning Memory зафиксировала "кампании в VK Ads для B2B-сегмента показывали низкую эффективность в трёх предыдущих проектах" — эта закономерность будет доступна PPC Agent как контекст, а не потребует, чтобы он "заново наступал на грабли".

Это и есть механизм предотвращения повторения ошибок (директива, раздел Learning) — не отдельная проверка "не повторяй ошибку X", а обычный контекст, который агент учитывает наравне с KB.

## 3. Единичный случай vs закономерность

Один неудачный результат не должен сразу становиться "правилом" — иначе система начнёт делать поспешные выводы из случайности. Поэтому:
- **Единичное наблюдение** хранится, но помечается как таковое — не влияет сильно на поведение агента.
- **Закономерность** (несколько похожих наблюдений подряд, зафиксированных Reflection) повышает "уверенность" урока — только тогда он начинает заметно влиять на решения агента (например, PM Agent может заранее предупредить вас на Strategy-gate: "по опыту, этот канал слабо работает для такого сегмента").

## 4. Обмен опытом между тенантами (закрывает Open Question из Memory System)

Решение: по умолчанию Learning Memory — на уровне тенанта (опыт одного клиента не переходит к другому автоматически). Но вводится управляемое исключение:

**Обобщённый урок** — если закономерность подтверждена на нескольких *разных* тенантах одного владельца (Контур A, Owner), она может быть предложена для переноса на уровень Domain (аналогично общему домену Knowledge Base), но **только через подтверждение** — по той же логике, что значимые факты в KB (см. Knowledge Base, раздел 2). Это защищает от утечки специфики одного клиента под видом "общей мудрости" и одновременно позволяет White-label пользователям получать пользу от общего опыта, когда это безопасно.

## 5. Пример возможного конфликта

Если Learning Memory говорит "разговорный стиль лучше для сегмента 18-25", а Knowledge Base клиента говорит "у этого клиента строгий формальный бренд-гайд" — приоритет у Knowledge Base (подтверждённый факт про конкретного клиента побеждает статистический вывод из опыта, см. Memory System раздел 2 про разницу источников доверия). Learning Memory не переопределяет прямые указания о клиенте.

## Open Questions

1. **Порог "закономерности" (раздел 3).** Сколько похожих наблюдений нужно, чтобы урок считался закономерностью, а не случайностью? Требует калибровки на практике — предлагаю не фиксировать число сейчас, вернуться после первых реальных проектов.
2. **Кто подтверждает перенос обобщённого урока на уровень Domain (раздел 4).** Вы лично, или это может быть частично автоматизировано при высокой уверенности? Предлагаю по умолчанию — всегда вы, пересмотреть при накоплении практики (симметрично с Knowledge Base, Open Question п.1).
