# Logging / Audit

Статус: Draft v0.1 — на ревью
Назначение: описать, что именно записывается о работе каждого агента, и как по этим записям можно полностью восстановить историю выполнения любого Project.

Простыми словами: это "журнал смен" в агентстве — кто, когда, что делал, какое решение принял, что пошло не так. Если через месяц вы захотите понять, "почему в этом проекте выбрали именно такую рекламную стратегию" — ответ должен быть в этом журнале, а не потеряться.

Использует термины из [[Glossary]]. Реализует [[Functional-Requirements]] (FR-12) и [[Non-Functional-Requirements]] (NFR-7 — полнота аудита). Является подписчиком на все события из [[Events]] (раздел 2). Хранится как EVENT в [[Database]].

---

## Purpose

Зафиксировать состав записи журнала (по директиве) и гарантировать, что по журналу восстановима вся история Project — это единственный источник данных для Recovery (следующий документ) и Reflection System.

## Scope

Документ описывает: обязательные поля записи, правило "ничего не пропускается", связь с Events, и вопрос хранения/доступа к логам. Не описывает: техническую реализацию хранения (Database уже задаёт структуру EVENT), политику удаления логов (Security).

---

## 1. Обязательные поля записи (по директиве)

Каждая запись журнала обязана содержать:

| Поле | Простыми словами |
|---|---|
| Идентификатор проекта | К какому Project относится |
| Идентификатор задачи | К какой Task относится |
| Агент | Кто именно выполнял (какая роль) |
| Время начала | Когда агент начал работу над Task |
| Время окончания | Когда закончил |
| Используемые инструменты | Какие Tool/MCP-серверы были вызваны (Tool Integration, MCP Integration) |
| Принятые решения | Что агент решил и почему (например, "выбраны такие ключевые слова, потому что...") |
| Ошибки | Что пошло не так технически |
| Предупреждения | Что не является ошибкой, но достойно внимания (например, Needs Revision) |
| Результат выполнения | Success / Needs Revision / Failed (Agent Framework, раздел 4) |

## 2. Связь с Events

Logging/Audit не отдельный, независимо работающий механизм — он подписан на **все** события из Events (Events, раздел 2, "Logging/Audit подписан на все события без исключения"). Каждое событие (Task Started, Task Succeeded, Plan Approved и т.д.) автоматически становится записью журнала. Это гарантирует NFR-7 — не может существовать событие, которое произошло, но не попало в журнал, так как запись в журнал и есть способ, которым событие сохраняется.

## 3. Принцип "ничего не пропускается"

Даже на Fast Execution Tier, где сокращается глубина промптов и проверок (Workflow Engine, раздел 2; Prompt Architecture, раздел 2), журналирование не сокращается — фиксируется всё то же самое, что и на Standard. Простыми словами: можно делать работу быстрее и проще, но нельзя переставать записывать, что было сделано — иначе Recovery (следующий документ) и Reflection не смогут работать на таких проектах (это прямо отмечено как открытый вопрос ранее, в Reflection System, раздел "Open Questions").

## 4. Кто может читать журнал

По умолчанию — вы (владелец Project/тенант), система (Recovery, Reflection). Соответствует мультитенантной изоляции (NFR-1, NFR-14, Database раздел 1) — журнал одного тенанта не виден другому. Детальный вопрос "видит ли White-label клиент журнал целиком, или только упрощённый прогресс" — открытый вопрос ниже (пересекается с Product Specification, раздел про то, что видит пользователь).

## 5. Пример на referensном сценарии

Через полгода после проекта "настроить рекламные кампании" вы можете открыть журнал и увидеть: Research начал в 10:00, закончил в 10:14, использовал инструмент просмотра сайта; PPC Agent начал в 10:15, использовал MCP-подключение к Google Ads, принял решение "бюджет распределён 60/40 между Google Ads и VK Ads, потому что Research показал больше органического трафика из Google"; QA вернул Needs Revision по причине "не хватает обоснования выбора аудитории"; после доработки — Success. Это и есть "восстановимая история" (Vision, раздел 1).

## Open Questions

1. **Что из журнала видит White-label клиент/специалист (раздел 4).** Полный журнал (все технические детали) может быть избыточен и не нужен конечному пользователю White Label — возможно, нужен "человекочитаемый" срез, а не сырой журнал. Предлагаю закрыть при проработке UX на Этапе 2, не блокирует архитектуру.
2. **Срок хранения журнала.** Не определён — вопрос политики (Security), не структуры.
