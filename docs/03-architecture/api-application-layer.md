## Purpose

Закрыть разрыв, найденный независимым ревью: до этого документа примерно половина Functional Requirements (всё, что касается прямого взаимодействия пользователя) не имела архитектурного описания, кроме одной подписи на диаграмме.

## Scope

Документ описывает: аутентификацию (в текущем, сознательно упрощённом виде), контракт создания Project, контракт паузы/возобновления на Strategy-gate, механизм просмотра прогресса, механизм уведомления о завершении (сейчас — заглушка), точку внедрения брендирования для White Label. Не описывает: конкретную реализацию UI (Этап 2), сам протокол Telegram-бота (появится отдельно, когда будет токен — см. раздел 4).

## 1. Аутентификация (текущее сознательное упрощение)

**Решение (2026-08-04):** на первой итерации системой пользуетесь только вы — полноценная аутентификация (регистрация, пароли, множество пользователей) не реализуется. Технически это означает: один тенант (Owner), доступ к системе — без публичного экрана входа, до момента, когда встанет задача показывать платформу другим пользователям.

**Важно для архитектуры:** это упрощение UI/входа, а не упрощение модели данных — `tenant_id` и row-level security (Database, Security) реализуются полноценно с первой итерации независимо от того, что реального "экрана логина" пока нет. Это значит, что включение полноценной аутентификации в будущем (Backlog) — это добавление слоя входа поверх уже готовой изоляции, а не переделка хранения данных.

## 2. Создание Project (FR-1, FR-2, FR-2a)

Точка входа принимает: URL сайта, описание бизнеса, продукт, маркетинговую задачу, выбранный Approval Level (по умолчанию Strategy-gate), выбранный Execution Tier (Fast/Standard). По приёму — создаётся PROJECT (Database) и запускается PM Agent (Workflow Engine, раздел 1).

## 3. Контракт паузы/возобновления на Strategy-gate (FR-2, детализация Workflow Engine раздел 3)

Раньше это было отмечено как открытый вопрос ("что именно показывается на паузе"). Закрываю здесь минимально необходимым для Этапа 2 контрактом:

- Система переводит Project в статус "ожидает подтверждения плана" и делает план (список ролей и порядок, построенный PM Agent) доступным для просмотра.
- Пользователь выполняет одно из двух действий: **подтвердить** (Project переходит в исполнение) или **отклонить с комментарием** (PM Agent строит план заново с учётом комментария).
- Технически это обычный запрос/ответ (нет необходимости в realtime-канале для этого шага — соответствует уже принятому решению NFR-8, "достаточно periodic pull").

## 4. Просмотр прогресса и уведомление о завершении (FR-3, FR-4, NFR-8, NFR-9)

**Прогресс (FR-3):** реализуется как обычный запрос состояния Project (periodic pull, NFR-8) — при каждом открытии статуса возвращается текущее состояние графа Task (Events/Logging-Audit, раздел "прогресс").

**Уведомление о завершении (FR-4, NFR-9 — гарантированная доставка):** решение (2026-08-04) — канал доставки: **Telegram-бот**, который будет подключён отдельно, когда вы предоставите токен бота. **На первой итерации (пока бота нет) этот функционал не реализуется** — гарантия доставки (NFR-9) на это время ослаблена до "статус доступен при просмотре прогресса", без проактивного уведомления. Это сознательное временное отступление от NFR-9, а не отмена требования — как только Telegram-бот подключён, NFR-9 реализуется полноценно через него.

## 4a. Получение результата и запрос доработки (FR-5, FR-6)

**Получение результата (FR-6):** по завершении Project (статус Project Completed, Events) точка входа отдаёт Project Output — гибкий набор материалов, собранный Report Generator Agent из результатов только тех ролей, что были задействованы (Functional Requirements, FR-6, решение от 2026-08-04). Это отдельный, самостоятельный запрос, не совпадающий с запросом прогресса (раздел 4) — прогресс отдаёт статус, эта точка отдаёт готовые материалы.

**Запрос доработки (FR-5):** доступен только для Project в статусе Completed. Пользователь отправляет комментарий/уточнение — система создаёт новую Task в рамках **того же** Project (не новый Project, переиспользуется Project Memory — Product Specification, раздел 2.1), направленную тому же PM Agent для перепланирования затронутой части Workflow. Approval Level и Execution Tier исходного Project наследуются, если не указано иное.

## 5. Точка внедрения брендирования (FR-8, White Label)

Хотя White Label не активен на первой итерации (референсный сценарий — Owner), точка для брендирования архитектурно закладывается уже сейчас, чтобы не потребовалось переделывать API-слой позже: любой ответ, содержащий Project Output или уведомление, проходит через слой оформления, который для тенанта типа "White-label клиент" подставляет его бренд, а для Owner — не подставляет ничего лишнего. Реализация самого оформления — Этап 2, вне документации.
