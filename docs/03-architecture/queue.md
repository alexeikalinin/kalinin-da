# Queue

Статус: Draft v0.1 — на ревью
Назначение: описать, как задачи (Task) физически передаются от Workflow Engine к конкретным агентам, когда те не могут (или не должны) выполняться мгновенно один за другим.

Простыми словами: если Workflow Engine — это диспетчер, который решает "кто следующий", то Queue — это "стол с входящими документами" у каждого агента. Диспетчер кладёт туда задачу, агент забирает её, когда освобождается, и кладёт результат обратно диспетчеру. Это нужно, потому что агенты часто работают не мгновенно и не одновременно освобождаются — без такого "стола" пришлось бы заставлять всех ждать друг друга по очереди даже там, где это не нужно.

Использует термины из [[Glossary]]. Реализует параллелизм, требуемый [[Workflow-Engine]] (раздел 2, Execution Tier) и [[Non-Functional-Requirements]] (NFR-5, NFR-11). Опирается на [[Architecture-Overview]] (ADR-0001 — Vercel + Supabase).

---

## Purpose

Зафиксировать, зачем в системе нужна очередь, что через неё передаётся, и как она обеспечивает параллельность (Fast Execution Tier) и горизонтальный масштаб (NFR-11), не привязываясь к деталям конкретной технологии.

## Scope

Документ описывает: что кладётся в очередь, кто кладёт и кто забирает, как обеспечивается параллелизм и что происходит, если агент "завис" или недоступен. Не описывает: конкретный программный продукт очереди (это Deployment/Architecture Overview — уже частично закрыто ADR-0001, так как в связке с Vercel Workflow DevKit управление очередью в основном скрыто внутри самого движка), формат Event (см. Events).

## 1. Что кладётся в очередь

Не сырые данные, а **Task-задание**: какая роль должна сработать, с каким входом (Product Specification, Agent Framework раздел 1). Пример: "PPC Agent, вот тебе результат Research, начинай".

## 2. Кто кладёт и кто забирает

- **Кладёт:** Workflow Engine — как только по графу (см. Workflow Engine, раздел 1) становится понятно, что Task готова к запуску (все её предпосылки выполнены).
- **Забирает:** конкретный экземпляр агента нужной роли, как только освобождается.

Важное свойство: Task лежит в очереди до тех пор, пока её не заберут — это не "прямой звонок" одному конкретному агенту, а "доска объявлений", с которой любой свободный исполнитель нужной специальности может взять работу. Это то, что даёт горизонтальный масштаб (NFR-11): если задач по роли SEO много одновременно, можно запустить несколько экземпляров SEO Agent, разбирающих одну очередь.

## 3. Как это даёт параллелизм (связь с Execution Tier)

Пример из Workflow Engine (PPC и Media Buyer после Research, независимо друг от друга): Workflow Engine кладёт в очередь сразу обе Task, как только Research закончен. Если оба агента свободны — они оба начинают работать одновременно, а не по очереди. Это и есть механизм, которым Fast Execution Tier достигает своей скорости (NFR-5) — параллелизм не "магия", а прямое следствие того, что обе Task оказались в очереди одновременно, и им не нужно ждать друг друга.

## 4. Что если агент "завис" или недоступен

- Task, которую забрали, но не завершили за разумное время — считается зависшей и возвращается обратно в очередь (может быть подхвачена другим экземпляром той же роли).
- Task, которая пролежала в очереди слишком долго, не будучи забранной (например, роль перегружена) — не теряется, а фиксируется как задержка через Logging/Audit; точный порог и что происходит дальше — уточняется в Recovery (Open Question ниже).

## 5. Изоляция между тенантами в очереди (уточнено по итогам независимого технического ревью)

Соответствует NFR-1/NFR-2/NFR-14: Task в очереди помечена принадлежностью к конкретному Project/тенанту. Независимое ревью пакета документации (Finding 2) справедливо указало, что формулировка "агент получает доступ только к контексту своего тенанта" изначально не была подкреплена механизмом — при горизонтальном масштабировании (несколько экземпляров одной роли разбирают общую очередь, раздел 2) обычная ошибка в коде теоретически могла бы привести к тому, что данные/ключи одного тенанта окажутся в обработке чужой Task, и это не было бы поймано на уровне RLS (RLS защищает БД, а не память исполняющегося процесса).

**Уточнённый принцип — неизменяемый контекст на вызов, без разделяемого состояния:**

- При заборе Task из очереди агент получает **неизменяемый (immutable) контекст исполнения**, содержащий `tenant_id` этой конкретной Task — контекст не может быть подменён или переиспользован для другой Task в рамках того же процесса/воркера.
- Исполнение Task не имеет доступа к какому-либо разделяемому изменяемому состоянию (общему кешу, глобальной переменной, переиспользуемому клиенту с "залипшими" учётными данными) между разными вызовами одного и того же воркера — каждый вызов логически независим, даже если физически выполняется на переиспользуемом вычислительном ресурсе.
- Учётные данные для MCP (MCP_CREDENTIAL, см. MCP Integration раздел 3) запрашиваются заново на каждый вызов по `tenant_id` из неизменяемого контекста, а не кешируются/передаются заранее — это устраняет путь, которым устаревший или чужой ключ мог бы "прилипнуть" к воркеру.

Это не отменяет и не заменяет row-level security на уровне БД — это дополнительный, независимый уровень защиты именно там, где RLS не действует (Queue/AgentRuntime/MCP-вызов).

**Реализация (добавлено 2026-08-04):** Queue не имеет отдельного пакета в Repository Structure — сама очередь физически скрыта внутри Vercel Workflow DevKit (ADR-0002). Логика, которая наша (изоляция контекста на вызов, обнаружение зависших задач), реализована в `packages/workflow-engine/src/dispatch.ts` и `queue-policy.ts`, рядом с графом/состоянием, от которых она зависит.

## Open Questions

1. **Порог "зависшей" Task.** Через какое время Task считается зависшей и возвращается в очередь? Зависит от Execution Tier (Fast — короткий порог, Standard — длиннее). Предлагаю закрыть числами в Recovery, здесь фиксируется только сам механизм.
2. **Что делать с Task, которая долго ждёт в очереди из-за перегрузки роли.** Здесь только зафиксировано, что это не теряется — конкретное поведение (эскалация вам? автоматическое масштабирование?) относится к Scaling.
