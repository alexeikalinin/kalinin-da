# Cost Optimization

Статус: Draft v0.1 — на ревью
Назначение: описать, как система выбирает конкретную модель (LLM) под конкретную задачу, чтобы не тратить дорогие ресурсы там, где не нужно — прямое требование директивы ("использование самой дорогой модели для всех задач запрещено").

Простыми словами: не каждую задачу в агентстве поручают самому опытному (и самому дорогому) специалисту. Простую и понятную работу может сделать младший сотрудник быстро и дёшево, а сложную и ответственную — стоит доверить более опытному, даже если это дороже и дольше. Cost Optimization Router — это то, что принимает это решение автоматически для каждой Task.

Использует термины из [[Glossary]]. Реализует [[Functional-Requirements]] (FR-15) и [[Non-Functional-Requirements]] (NFR-12, NFR-13). Опирается на [[Architecture-Overview]] (ADR-0003 — Anthropic на первой итерации + абстракция над провайдером) и [[Prompt-Architecture]] (раздел 5 — независимость сборки промпта от выбора модели).

## Purpose

Зафиксировать, по каким критериям выбирается модель под задачу, и как это остаётся прогнозируемым по стоимости (NFR-12) — без привязки к конкретному провайдеру, чтобы решение не пришлось переделывать при будущем расширении (ADR-0003).

## Scope

Документ описывает: критерии выбора модели, связь с Execution Tier, оценку стоимости Project до начала работы. Не описывает: конкретные тарифы/цены моделей (это быстро устаревающая деталь реализации, не архитектура), сам протокол вызова провайдера (Prompt Architecture, раздел 5, уже отделяет это).

## 1. Критерии выбора модели (по директиве: стоимость, качество, скорость, сложность)

| Критерий | Простыми словами | Как влияет |
|---|---|---|
| Сложность задачи | Насколько задача творческая/ответственная (например, стратегия vs форматирование текста) | Более сложная задача → более способная (и обычно более дорогая) модель |
| Execution Tier | Fast или Standard (Product Specification, Functional Requirements FR-2a) | Fast тяготеет к более быстрым/дешёвым моделям, Standard допускает более дорогие там, где это оправдано |
| Approval Level | Strategy-gate или Output-only | Задачи, которые в любом случае будут проверены вами на Strategy-gate, могут позволить себе более дешёвую модель на черновом этапе — окончательная проверка всё равно ваша |
| Роль | Какая специализация выполняет Task | Некоторые роли по своей природе требовательнее к качеству модели (например, формирование стратегии у PM Agent), другие — нет (например, формальная проверка формата у QA) |

## 2. Как это работает на практике (пример на referensном сценарии)

Задача "написать 20 вариантов коротких рекламных объявлений" (Copywriter, Fast Execution Tier) — рутинная, легко проверяемая работа, не требует самой мощной модели. Задача "сформировать общую стратегию продвижения" (PM Agent, Standard) — требует более развитого понимания контекста, оправдывает более способную модель. Router выбирает модель именно так, а не по принципу "одна модель для всех Task Project" — то есть выбор происходит на уровне отдельной Task, а не всего Project целиком.

## 3. Прогнозируемость стоимости (NFR-12)

До начала исполнения Project можно дать приблизительную оценку стоимости, зная: сколько ролей будет задействовано (PM Agent решает это при построении плана — Workflow Engine, раздел 1), какой Execution Tier выбран, и типичную стоимость Task для каждой роли (накапливается по опыту прошлых Project — тоже часть Learning Memory, только не про маркетинговые решения, а про операционные показатели). Это не точная цифра, а ориентир — точная стоимость известна только по факту выполнения.

**Холодный старт (уточнено по итогам независимого технического ревью):** для самых первых Project (пока нет накопленной операционной статистики) типичная стоимость по роли не может быть взята "по опыту" — её ещё не существует. На этот период используется грубая оценка по умолчанию (например, исходя из известной стоимости вызова модели каждого уровня и ожидаемого числа вызовов на роль, без уточнения по фактическим данным) — как только накапливается статистика по первым Project, оценка переходит на реальные цифры автоматически, без отдельного решения.

## 4. Независимость от провайдера (реализация ADR-0003)

Router работает с абстрактным понятием "уровень модели" (например, условно "быстрая/базовая/продвинутая"), а не с названием конкретной модели конкретного провайдера. Сегодня это реализуется через линейку моделей Anthropic; при появлении экономической необходимости (например, после решения открытого вопроса юнit-экономики White Label из Business Goals) добавление другого провайдера — это добавление новой реализации за тем же понятием "уровень модели", а не пересмотр Router или Agent Framework.

## Open Questions

1. **Точное сопоставление "сложность/роль/tier → уровень модели".** Это калибровочная таблица, которую разумно уточнять на практике (референсный сценарий), а не придумывать заранее — архитектурное решение здесь фиксирует только принцип, не числа/названия моделей.
2. **Юнит-экономика White Label** (перенесено из Business Goals, Open Question п.2) — всё ещё открыт, но не блокирует архитектуру: Router уже спроектирован так, чтобы дать данные (раздел 3), нужные для решения этого вопроса, когда вы будете к нему готовы.
