# Prompt Architecture

Статус: Draft v0.1 — на ревью
Назначение: описать, как именно формируется текст, который агент отправляет модели (LLM) — из каких частей он собирается, откуда берутся эти части, и как это связано с уже принятыми решениями (уровни памяти, KB, уроки, Execution Tier).

Простыми словами: если Agent Framework — это должностная инструкция, то Prompt Architecture — это то, как эта инструкция реально "зачитывается" модели перед началом работы, вместе со всем нужным контекстом — как бриф, который дают сотруднику перед началом задачи: что нужно сделать, что важно знать про клиента, чему мы научились из прошлых похожих задач.

Использует термины из [[Glossary]]. Реализует контракт агента ([[Agent-Framework]], элемент "Модели"/"Входные данные"), использует уровни памяти из [[Memory-System]], [[Knowledge-Base]], [[Learning-System]]. Опирается на [[Architecture-Overview]] (ADR-0003 — абстракция над провайдером).

---

## Purpose

Зафиксировать структуру промпта как набор чётко определённых, переиспользуемых частей — чтобы: (а) любая новая роль собирала промпт по одному и тому же принципу; (б) Reflection мог оценивать "эффективность промптов" (FR-14) осмысленно, сравнивая версии; (в) смена LLM-провайдера в будущем (ADR-0003) не требовала переписывания логики сборки промпта, только адаптации формата вызова.

## Scope

Документ описывает: из каких блоков состоит промпт, откуда каждый блок берётся, как версионируются шаблоны, как Execution Tier влияет на объём контекста. Не описывает: конкретные формулировки промптов для конкретных ролей (это будущая работа Agent Architect при написании каждой роли), технические детали вызова конкретного LLM API (Tool Integration/Deployment).

---

## 1. Из каких блоков собирается промпт

Промпт для любого агента — это не один сплошной текст "от руки", а сборка из блоков, каждый со своим источником:

| Блок | Что содержит | Источник |
|---|---|---|
| **Роль** | Назначение и ответственность агента (не меняется от задачи к задаче) | Agent Framework, спецификация роли |
| **Задача** | Конкретная Task, которую нужно выполнить сейчас | Workflow Engine (то, что передано через Queue) |
| **Факты о клиенте** | Проверенные факты — бренд, ограничения, история | Knowledge Base (Client KB) |
| **Общие знания домена** | Профессиональный контекст (как устроен канал/инструмент) | Knowledge Base (Domain KB) |
| **Прошлый опыт** | Релевантные "уроки" — что сработало/не сработало в похожих ситуациях | Learning Memory (через Learning System) |
| **Контекст проекта** | Что уже сделали другие агенты в этом Project | Project Memory |
| **Ограничения** | Бюджет по времени/стоимости, связанные с Execution Tier | Workflow Engine / Cost Optimization Router |

Простыми словами: агент получает не "голую" задачу, а задачу + бриф о клиенте + то, чему система уже научилась + что уже сделали коллеги по этому проекту — ровно так, как ввели бы в курс дела нового сотрудника перед стартом.

## 2. Как Execution Tier влияет на промпт

Не меняет блоки, но меняет их **глубину**:
- **Fast:** краткая версия каждого блока — только самое существенное (например, 2-3 ключевых факта о клиенте, а не полная история).
- **Standard:** более полный контекст — больше фактов, больше релевантных уроков, детальнее задача.

Это прямое продолжение решения из Workflow Engine (раздел 2) — Execution Tier везде реализуется как "настройка глубины", а не отдельная ветка логики.

## 3. Версионирование промптов (нужно для оценки эффективности, FR-14)

Каждый шаблон блока "Роль" (то, как сформулировано назначение/инструкция для конкретной роли) имеет версию. Когда Reflection анализирует "эффективность промптов" (Reflection System, раздел 2), он сравнивает результат по конкретной версии шаблона — это позволяет увидеть, стала ли новая формулировка лучше или хуже старой, а не просто "промпт вообще работает нормально".

Простыми словами: если мы меняем формулировку инструкции для Copywriter Agent, мы не теряем историю старой версии — можем увидеть, действительно ли новая формулировка снизила число доработок (Needs Revision) по сравнению со старой.

## 4. Кто пишет и меняет шаблоны

По аналогии с Agent Framework (раздел 4a) — начальный шаблон блока "Роль" для новой роли предлагает Agent Architect вместе со спецификацией роли, требует вашего утверждения. Дальнейшие изменения версии шаблона могут быть также предложены на основе находок Reflection (Reflection System, раздел 4) — но, как и любое изменение контракта роли, финальное утверждение новой версии — за вами (не автоматическая самомодификация промптов без контроля, что соответствует принципу директивы "критичные решения не принимаются автономно").

## 5. Независимость от LLM-провайдера (реализация ADR-0003)

Сборка блоков (разделы 1-2) не зависит от того, какая модель в итоге вызывается — это происходит уже после сборки, когда Cost Optimization Router выбирает конкретную модель под Execution Tier/сложность. Формат итогового вызова (как именно блоки упаковываются в конкретный API-запрос) — это адаптер под конкретного провайдера, отдельный от логики сборки контента. Это и даёт то, что смена/добавление провайдера в будущем не требует переписывания Prompt Architecture — только адаптера вызова.

## Open Questions

1. **Что делать, если собранный промпт (все блоки вместе) становится слишком большим** (например, у клиента огромная история в Company Memory) — обрезать по приоритету блоков, суммаризировать, или это должно быть ограничением Execution Tier? Предлагаю закрыть при проектировании Cost Optimization, так как это прямое стоимостное решение.
2. **Формат хранения версий шаблонов** — отдельная таблица версий, или просто история изменений в Agent Framework спецификации роли? Техническая деталь, откладываю до Database.
