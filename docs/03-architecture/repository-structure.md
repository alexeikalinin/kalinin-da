# Repository Structure

Статус: Draft v0.1 — на ревью
Назначение: описать, как будет организован код на Этапе 2 — где что будет лежать, чтобы структура кода отражала архитектуру, а не была случайной свалкой файлов.

Простыми словами: это "план офисных кабинетов" — где сидит диспетчер, где сидят исполнители ролей, где хранится общая база знаний. Сейчас (Этап 1) кабинеты пустые — мы просто расставляем таблички на дверях заранее, чтобы потом не переставлять мебель.

Использует термины из [[Glossary]]. Отражает решения [[Agent-Framework]], [[Workflow-Engine]], [[Coding-Standards]], [[Architecture-Overview]] (ADR-0001).

Разрешена только структура (план), не код — production-код запрещён на Этапе 1.

## Purpose

Дать однозначный ответ "куда положить новый файл", когда начнётся реализация — чтобы структура репозитория не изобреталась заново в момент написания первой строки кода, а уже была решена здесь, согласованно с архитектурой.

## Scope

Документ описывает: верхнеуровневую структуру папок кода (Этап 2), соответствие каждой папки конкретному документу из раздела 03-architecture. Не описывает: содержимое файлов, конфигурацию сборки.

## 2. Правило соответствия "документ → папка"

Каждая папка в `packages/` соответствует ровно одному документу из `docs/03-architecture/` — если в будущем появляется код, не укладывающийся ни в одну существующую папку, это сигнал, что либо нужна новая папка (и, возможно, новый документ), либо код на самом деле относится к уже описанному месту, и это нужно осмыслить, а не просто "куда-то положить".

## 2a. Почему у Queue нет своей папки (добавлено 2026-08-04)

`docs/03-architecture/queue.md` существует как документ, но не имеет отдельной папки в `packages/` — сама очередь физически скрыта внутри Vercel Workflow DevKit (ADR-0002), поэтому "реализовывать" по сути нечего отдельно от Workflow Engine. Наша собственная логика (изоляция контекста на вызов, обнаружение зависших задач) живёт в `packages/workflow-engine/`. Это пример правила из раздела 2: столкнувшись с этим при реализации, мы не стали создавать пустую папку `queue/`, а осознанно расширили существующую.

## 2b. Почему у Logging/Audit нет своей папки (добавлено 2026-08-05)

Та же логика, что в разделе 2a. `docs/03-architecture/logging-audit.md` сам говорит про себя: "не отдельный, независимо работающий механизм — он подписан на все события из Events" (раздел 2). Реализация (`attachLogSink`, подписывающийся на "*"; `reconstructJournal`, восстанавливающий обязательные поля журнала из потока событий) живёт в `packages/events/src/journal.ts`, а не в отдельной папке `logging-audit/`.

## 2c. `packages/reference-scenario` — исключение из правила "один документ → одна папка" (добавлено 2026-08-06)

В отличие от разделов 2a/2b (где код жил внутри уже существующего пакета вместо пустой новой папки), здесь обратный случай: понадобилась новая папка, не привязанная ни к одному конкретному документу раздела 03-architecture, а проверяющая веху "Год 1" из `01-vision/business-goals.md` — то, что весь референсный конвейер (все 6 ролей) реально работает вместе через граф Workflow Engine. Это осознанное исключение: интеграционный прогон, зависящий от всех ролей и инфраструктурных пакетов сразу, логически стоит "над" ними, а не "рядом" с одним из них.

## 2d. `packages/agents/ceo`, `packages/agents/pm` — не было в исходном списке (добавлено 2026-08-12)

Раздел 1 перечислял только референсный маркетинговый конвейер (Research…Report Generator) и служебные роли (Agent Architect, Reflection) — CEO и PM Agent из Glossary раздела 2 в исходный список `packages/agents/` не попали. Добавлены по прямому запросу пользователя: PM Agent — не формальность, а первая реальная реализация построения графа (`buildGraph` на основе выбора модели, а не вручную прописанный граф, как во всех предыдущих тестах, включая `@ama/reference-scenario`). CEO Agent принимает вход Project и формирует стратегию, которую PM Agent использует при декомпозиции.

## 3. Почему `agents/` — папка с множеством подпапок, а не один файл

Прямое отражение решения из Agent Framework (раздел 5): каждая роль — независимый модуль, реализующий общий интерфейс `agent-framework`. Новая роль (например, будущая "email-маркетинг") — это новая подпапка в `agents/`, не изменение существующих.
