# Memory System

Статус: Draft v0.1 — на ревью
Назначение: описать, где и как система хранит "память" — от сиюминутного контекста одной задачи до накопленного за годы опыта. Каждый уровень памяти должен иметь чёткие правила: кто может туда писать, кто читать, когда это удаляется.

Простыми словами: у любого сотрудника есть разные виды памяти. Есть то, что он помнит только пока делает конкретное поручение (и забывает через час). Есть то, что он помнит про текущий проект клиента. Есть то, что помнит вся компания про клиента годами (например, "этот клиент не любит слишком яркие цвета"). А есть общие профессиональные знания ("как вообще работает SEO"), которые не зависят от конкретного клиента. Memory System — это именно разделение системы на такие "виды памяти", чтобы ничего не терялось не вовремя и не утекало не туда.

Использует термины из [[Glossary]] (Session/Task/Project/Company Memory, Knowledge Base, Learning Memory — определения там). Реализует [[Non-Functional-Requirements]] (NFR-1, NFR-2 — мультитенантная изоляция) и опирается на [[Architecture-Overview]] (ADR-0001 — Supabase/Postgres RLS).

---

## Purpose

Дать однозначные правила чтения/записи/удаления для каждого уровня памяти, чтобы Database, Agent Framework (раздел "Память" в контракте агента) и Cost Optimization могли проектироваться без домысливания того, что можно, а что нельзя писать в каждый уровень.

## Scope

Документ описывает шесть уровней памяти, правила CRUD (создание/чтение/изменение/удаление) для каждого, и границу между Knowledge Base и Learning Memory (открытый вопрос из Glossary — закрывается здесь). Не описывает: физическую схему таблиц (Database), алгоритм самого обучения (Learning System).

## 1. Уровни памяти и правила

| Уровень | Живёт | Кто пишет | Кто читает | Когда удаляется |
|---|---|---|---|---|
| **Session Memory** | Одна Session (Glossary) | Любой Agent в рамках текущей сессии | Только текущая Session | Автоматически по завершении Session — если что-то важно, до этого момента должно быть перенесено на уровень Task/Project |
| **Task Memory** | Одна Task | Agent, выполняющий Task | Тот же Agent, QA Agent при проверке, Workflow Engine (для передачи следующему шагу) | По завершении Task Memory архивируется в Project Memory (не удаляется полностью — иначе Recovery/Reflection не смогут её увидеть) |
| **Project Memory** | Весь Project, включая повторные Session (например, после Recovery) | Любой Agent в рамках Project, Workflow Engine (статусы) | Любой Agent, работающий в этом Project; пользователь (при просмотре прогресса, FR-3) | Не удаляется автоматически — хранится минимум до Reflection по Project; долгосрочное хранение — вопрос политики хранения данных (Security) |
| **Company Memory** | Всё время сотрудничества с конкретным тенантом (Owner или White-label клиентом) | Явно — не automatически каждым Agent, а через утверждённое обновление (например, по итогам Reflection, см. раздел 2) | Любой Agent, работающий на этого тенанта, в любом его Project | Не удаляется автоматически, живёт пока жив тенант |
| **Knowledge Base (KB)** | Постоянно, не привязана к одному тенанту (общий домен) либо привязана к тенанту — см. раздел 3 | Через Agent Architect / явное подтверждение (не пишется агентом "по ходу дела" без проверки) | Любой Agent, которому нужен доступ к этому домену знаний | Не удаляется автоматически, пересматривается вручную при устаревании факта |
| **Learning Memory** | Постоянно | Только через Reflection (по итогам завершённого Project, см. Glossary) | Любой Agent, для которого это релевантно (например, все Copywriter Agent видят вывод "такой стиль текста не сработал у этого сегмента клиентов") | Не удаляется автоматически; может быть пересмотрено при накоплении противоречащих данных (уточняется в Learning System) |

## 2. Закрытие открытого вопроса из Glossary: KB vs Learning Memory

Открытый вопрос был: может ли агент писать в KB напрямую, минуя Reflection?

**Решение:** нет. Разница закрепляется так:
- **Knowledge Base** — факты, которые кто-то (Agent Architect, вы, или явно проверенный процесс) **подтвердил** как истину о домене/клиенте. Пример: "у этого клиента целевая аудитория — женщины 25-40".
- **Learning Memory** — выводы, которые система сделала **сама из опыта** через Reflection. Пример: "тексты в разговорном стиле для этого сегмента получают более высокую оценку QA".

Простыми словами: KB — это то, что нам сказали или мы явно проверили; Learning Memory — это то, чему система сама научилась, наблюдая за результатами. Прямая запись агентом в KB "по ходу работы" запрещена — это защищает от ситуации, когда непроверенное предположение одного агента становится "фактом" для всех остальных.

## 3. Мультитенантность памяти (реализация NFR-1, NFR-2)

- Session/Task/Project/Company Memory — **всегда** привязаны к конкретному тенанту (row-level security, ADR-0001), не могут быть прочитаны другим тенантом ни при каких условиях (соответствует NFR-14).
- Knowledge Base делится на две части: **общий домен** (например, "как устроена реклама в Google Ads вообще" — не содержит данных клиента, может быть общим для всех тенантов) и **KB конкретного клиента** (например, специфика бренда клиента — принадлежит тенанту, изолирована как и Company Memory).
- Learning Memory по умолчанию — на уровне тенанта (опыт одного клиента не "перетекает" в данные другого клиента без явного решения). Вопрос, стоит ли в будущем разрешить обмен неспецифичным опытом между тенантами (например, "разговорный стиль вообще работает лучше для сегмента 18-25", без привязки к клиенту) — открытый вопрос ниже.

## 4. Пример на referensном сценарии

Задача "настроить рекламные кампании" (ваш пример): Research Agent во время работы пишет находки в **Task Memory**; по завершении Task эти находки становятся частью **Project Memory**, доступной PPC/Media Buyer Agent. Если в ходе работы выясняется устойчивый факт про клиента (например, "у клиента уже был неудачный опыт с VK Ads") — это не пишется автоматически в KB, а помечается как предложение, которое либо вы подтверждаете (тогда попадает в Company Memory/KB клиента), либо это остаётся только в рамках Project Memory.

## Open Questions

1. **Обмен неспецифичным опытом Learning Memory между тенантами (раздел 3).** Может ускорить обучение системы в целом (особенно полезно для White Label — новые клиенты сразу получают пользу от опыта на других), но требует явной гарантии, что в обобщённый вывод не "просочились" данные конкретного клиента. Предлагаю не решать сейчас — отметить в Backlog и вернуться при проектировании Learning System.
2. **Кто именно подтверждает предложение агента для записи в KB/Company Memory (раздел 4).** Всегда вы лично, или это может делать, например, PM Agent по внутреннему правилу для несущественных фактов? Предлагаю закрыть при написании Knowledge Base (следующий документ).
