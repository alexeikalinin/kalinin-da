# Weekly campaign trend tracking

Статус: Implemented v1 — 2026-09-03
Назначение: дать возможность видеть перфоманс каждой кампании в динамике по неделям (не только "срез за период"), и автоматически ловить кампании, у которых CPA устойчиво растёт несколько недель подряд — для ЛЮБОГО текущего или будущего клиента через один и тот же механизм, без написания нового кода под клиента.

## Источник алгоритма

Портировано из `~/Documents/VibeCoding/Astrum Analyzer` — локального инструмента еженедельного PPC-анализа Warface (Astrum Entertainment), в частности `analysis/trend_alerts.py`'s `detect_sustained_degradation`. Это отдельный, изолированный проект (собственный git, свой локальный Supabase, LLM работает офлайн через Ollama) — код не импортировался, алгоритм прочитан и переписан на TypeScript под схему этого репозитория.

Ключевая идея алгоритма (сохранена как есть): **не строгая серия "неделя хуже предыдущей"**, а тренд в скользящем окне — рост CPA за N+1 недель считается реальной деградацией, даже если внутри окна была 1 "проседающая" неделя (терпимость к шуму), но не 2+.

## Что отличается от Warface-версии (и почему)

| Astrum Analyzer (Warface) | Этот репозиторий (generic) | Почему |
|---|---|---|
| Метрика — CPUser (spend / (FL+Rets)) | CPA (spend / approved-конверсии) | CPUser специфична для игровой воронки Regs→FL→Rets; CPA — то, что уже считает весь остальной код этого репозитория |
| Еженедельный снимок в `warface_analyses` — таблица, которую заполняет человек командой `cli.py analyze` | Никакой отдельной снимок-таблицы — агрегация по неделям на лету из `ad_stat` (уже пишется ежедневно существующим cron `sync-ad-stats`) | `ad_stat` уже есть и уже общий для всех клиентов — плодить вторую таблицу с той же информацией только ради "недельного среза" не нужно |
| Данные из Google Sheets (Dashboard Import) + сопоставление имён кампаний с Директом (`match_campaign`, нормализация имён, ремонт опечаток) | Не нужно — кампания и её метрики приходят из ОДНОГО источника (Google Ads/Yandex API), сопоставлять нечего | Специфика Warface (данные о конверсиях лежат в отдельной таблице, которую ведут руками) не существует для остальных клиентов |
| Диагноз степени деградации — Regs→FL conversion rate | CVR = conversions/clicks | Обобщение: любая платформа сводится к spend/clicks/conversions на этом уровне |
| `campaign_status` — своя таблица в локальном Supabase одного клиента | `campaign_status` — общая таблица, `client_id`+`platform`+`campaign_id`, синкается для всех клиентов разом | Тот же смысл (не путать "CPA растёт" с "кампания давно остановлена, это хвост показов"), но на уровне агентства, не одного клиента |

## Схема данных

- **`ad_stat`** (существовала до этой задачи, `0002_client_ad_accounts.sql`) — один ряд на (клиент, платформа, кампания, день). Заполняется ежедневным cron `apps/web/app/api/cron/sync-ad-stats`.
- **`campaign_status`** (новая, `0011_campaign_status.sql`) — один ряд на (клиент, платформа, кампания), перезаписывается при каждом синке. `is_running` — true только когда кампания реально может тратить (Google: `status === "ENABLED"`; Yandex: `State === "ON"`, не `Status`, т.к. `Status` — это статус модерации, кампания может быть `ACCEPTED`, но стоять на паузе через `State`).

Обе таблицы теперь синкаются вместе тем же cron-запуском (`apps/web/lib/sync-campaign-status.ts`, вызывается из `sync-ad-stats/route.ts` параллельно с `syncAdStats` через `Promise.allSettled` — сбой одного не валит другой).

## Код

`apps/web/lib/campaign-trends.ts`:
- `getWeeklyCampaignHistory(clientId, options)` — I/O: читает `ad_stat`+`campaign_status`, вызывает `aggregateWeeklySeries` (чистая функция).
- `aggregateWeeklySeries(rows, statusByKey, includeCurrentPartialWeek, today?)` — группирует по ISO-неделе (понедельник-воскресенье), считает CPA (`null`, если конверсий 0 — никогда не 0 как значение). Текущая, ещё не завершённая неделя по умолчанию исключается из выдачи (шум частичных данных), но может быть включена явно с флагом `isComplete: false`.
- `detectSustainedDegradation(clientId, options)` — I/O: тянет `getWeeklyCampaignHistory`, вызывает `computeDegradation` (чистая функция).
- `computeDegradation(series, options)` — прямой порт `detect_sustained_degradation`: окно `minWeeks+1` (по умолчанию 3+1=4) недель, допуск `maxDipSteps` проседаний (по умолчанию 1), порог суммарного роста `minTotalIncreasePct` (по умолчанию 20%), исключает остановленные кампании по `campaign_status`. Для каждой найденной деградации считает `hypothesis`/`recommendation` — те же четыре сигнала, что в Astrum (падение CVR, рост CPC, падение объёма при том же/сниженном расходе), тексты на русском.

Оба I/O-обёртки — тонкие, вся логика — в чистых функциях (то же разделение "детерминированный движок + I/O", что `analysis/metrics.py` в Astrum Analyzer). Покрыто юнит-тестами `apps/web/lib/campaign-trends.test.ts` (9 тестов, синтетические данные — недельная группировка, `cpa: null` при нуле конверсий, допуск на 1 проседание vs отказ при 2, разграничение гипотез "упала конверсия" vs "выросла цена клика", исключение остановленной кампании).

## Живая проверка (2026-09-03)

Прогнано против реальных данных Медавеню (37 кампаний, обе платформы, ~5 недель истории в `ad_stat`) с порогом `minWeeks: 2, minTotalIncreasePct: 15` (мягче дефолта — история пока короче обычных 4 недель). Нашло 11 реальных деградаций, включая те же кампании, что независимо всплывали в ручных аудитах этого дня (РСЯ Гинекология: CPA 0.75→71.46→100.01 BYN, +13235%; Дерматология; Проктолог; Невролог Взрослые) — совпадение с ручными находками подтверждает, что автоматический механизм ловит те же реальные проблемы, не шум.

## Как использовать для любого клиента

Ничего клиент-специфичного в коде нет — обе функции принимают только `clientId` (из таблицы `client`) и опциональные пороги. Как только у клиента заведён `client_ad_account` и работает ежедневный sync, `detectSustainedDegradation(clientId)` сразу доступен без единой строчки нового кода. Единственное, что можно донастроить под клиента — пороги (`minWeeks`/`minTotalIncreasePct`/`maxDipSteps`), если у него принципиально другая частота данных или волатильность.

## Подключение к ppc-agent и еженедельный cron (2026-09-03) — сделано

Добавлено новое, полностью детерминированное (без вызова модели — тот же принцип, что у `apply`/`verify`) действие `"trend-alerts"` у `packages/agents/ppc`:
- `packages/agents/ppc/src/ppc-agent.ts` — `handleTrendAlerts`: тянет алерты через toolId `"campaign-trends"`, сверяет с уже открытыми (`status: 'proposed'`) строками `campaign_changes_log` с `change_type: 'trend_degradation'` по тому же `campaignId` (чтобы не плодить дубликат каждую неделю, пока прошлый алерт ещё не рассмотрен), пишет только новые через toolId `"campaign-changes"`.
- `apps/web/lib/real-tools.ts` — новый toolId `"campaign-trends"`, дергает `detectSustainedDegradation`/`getWeeklyCampaignHistory` напрямую (read-only, без graceful-degrade — ошибки Supabase уже говорящие).
- `apps/web/lib/campaign-optimization-orchestrator.ts` — `runTrendAlerts(input)`, тот же паттерн, что `runApply`/`runVerify`.
- `apps/web/app/api/cron/detect-trend-alerts/route.ts` + `vercel.json` (`0 4 * * 1`, через час после ежедневного синка) — еженедельный Vercel Cron, перебирает все активные `client_ad_account` и вызывает `runTrendAlerts` на каждый.

Найденные алерты попадают в тот же `campaign_changes_log`, что и предложения `recommend` — человек видит их в уже существующем UI одобрения, отдельная страница не нужна.

**Живая проверка (2026-09-03)**: прогнано против реальных `client_ad_account` Медавеню (обе платформы) с `minWeeks: 2, minTotalIncreasePct: 15`. Первый прогон записал 7 алертов по Google Ads и 4 по Яндекс.Директу (`status: 'proposed'`) — реальные, соответствующие ранее найденным вручную деградациям (Дерматология, Проктолог, Невролог Взрослые, РСЯ Гинекология и др.), не тестовый мусор — оставлены в базе как первая партия предложений на ревью. Повторный прогон сразу после первого корректно отработал дедупликацию: `alertsFound: 7/4`, но `changeLogIds: []`, `skippedDuplicates: 7/4` — новых строк не создано.

## Известные ограничения

- Google Ads `conversions_total` в `ad_stat` — это `all_conversions` (дробное значение data-driven атрибуции), не целое число кликов-в-конверсию — это нормально для Google Ads, но стоит иметь в виду при чтении `cpaHistory` в чужом коде.
- Дедупликация — по одному открытому алерту на кампанию одновременно; если деградация усугубляется, а прошлый алерт всё ещё `proposed`, второй раз она не перезапишется/не обновится, пока человек не разберёт первый (approve/reject/apply) — обновление уже открытого алерта свежими цифрами не реализовано, это следующий шаг, если окажется нужным на практике.
- Нет отдельного порога/логики для промежуточных статусов кампании (совсем новая — 1-2 недели данных) на уровне cron — 0 алертов для свежего клиента ожидаемо, не является ошибкой.
