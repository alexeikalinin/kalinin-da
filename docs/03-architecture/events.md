# Events

Статус: Draft v0.1 — на ревью
Назначение: описать, какие "факты" фиксирует система по ходу работы (например, "Task завершена", "агент вернул ошибку") и кто на них реагирует. Это то, что связывает Workflow Engine, Queue, Logging/Audit и уведомления пользователя в одну картину.

Простыми словами: если Queue — это "стол с входящими задачами", то Event — это запись в журнале "что вообще произошло" каждый раз, когда что-то меняется. Например, когда официант приносит заказ на кухню — это событие "заказ принят"; когда блюдо готово — событие "блюдо готово". Разные части ресторана реагируют на разные события: кухня реагирует на "заказ принят", официант — на "блюдо готово". В нашей системе так же: разные подсистемы "подписаны" на разные события.

Использует термины из [[Glossary]]. Реализует [[Functional-Requirements]] (FR-3, FR-4, FR-12) и опирается на [[Queue]], [[Workflow-Engine]].

---

## Purpose

Зафиксировать перечень типов событий и правило "кто на что реагирует", чтобы Logging/Audit, уведомления о прогрессе (FR-3/FR-4) и будущий Recovery могли проектироваться на одном и том же наборе фактов, а не на разных представлениях о происходящем.

## Scope

Документ описывает: базовый набор типов событий, кто их порождает, кто на них подписан, и как это связано с уведомлением пользователя и прогрессом (NFR-8, NFR-9). Не описывает: техническую реализацию шины событий (Deployment/Architecture), формат хранения (Database).

## 1. Базовые типы событий

| Событие | Кто порождает | Пример из референсного сценария |
|---|---|---|
| Project Created | API / Application Layer | Project на "настройку рекламных кампаний" создан |
| Plan Ready | PM Agent | План (Research → PPC/Media Buyer → Analytics → QA → Report) построен |
| Plan Approved / Plan Rejected | Пользователь (через Strategy-gate) | Вы подтвердили или попросили изменить план |
| Task Queued | Workflow Engine | PPC Agent и Media Buyer Agent поставлены в очередь одновременно |
| Task Started | Agent (при заборе из очереди) | PPC Agent начал работу |
| Task Succeeded / Task Needs Revision / Task Failed | Agent (по протоколу ошибок, Agent Framework раздел 4) | PPC Agent вернул результат / попросил проверку / не смог выполнить |
| Task Stuck | Queue (по таймауту) | Agent завис — Task возвращена в очередь |
| Project Completed | Workflow Engine (когда граф полностью пройден) | Все роли отработали, Report Generator собрал результат |

Это не исчерпывающий список — это минимальный набор, достаточный для покрытия FR-3/FR-4/FR-12 на референсном сценарии; расширяется по мере необходимости без изменения механизма (см. раздел 3).

## 2. Кто на что подписан

- **Logging/Audit** подписан на **все** события без исключения (FR-12 — полнота журнала, NFR-7).
- **Прогресс, который видите вы (FR-3)** — строится из событий Task Queued/Started/Succeeded/Failed по конкретному Project; поскольку решено, что достаточно periodic pull (NFR-8), эти события не обязаны доставляться мгновенно — достаточно, чтобы они были записаны и доступны при следующем "взгляде" на статус.
- **Уведомление о завершении (FR-4)** подписано на Project Completed — и, в отличие от прогресса, по целевому требованию (NFR-9) должно быть доставлено гарантированно, а не просто "лежать и ждать, пока посмотрят". *(Временно, до подключения канала доставки — см. NFR-9, [[API-Application-Layer]] раздел 4 — фактически реализовано как раз через "доступно при просмотре", то есть текущая реализация сознательно отстаёт от целевого требования на этот период.)*
- **Recovery** (будущий документ) будет подписан на Task Stuck и Task Failed, чтобы решать, что делать дальше.
- **Reflection** (будущий документ) читает всю историю событий завершённого Project целиком, а не подписывается в реальном времени.

## 3. Почему это расширяемо (снова NFR-10)

Новая роль не создаёт новых типов событий — она использует тот же набор (Task Started/Succeeded/...), просто с другим именем роли внутри. Новый тип события потребовался бы только для принципиально нового вида факта (например, если в будущем появится Human-in-the-loop внутри Task, а не только на границах Project) — это осознанное расширение, а не что-то, что ломается при масштабировании числа ролей.

## Open Questions

1. **Формат содержимого события.** Здесь зафиксирован только перечень типов, не структура данных внутри каждого события (например, что именно лежит в Task Failed — только код ошибки, или ещё и что агент пытался сделать). Предлагаю закрыть в Logging/Audit, так как это в первую очередь его требование к детализации.
2. **Нужна ли пользователю более гибкая настройка того, какие события превращаются в видимые уведомления** (например, уведомлять и о Plan Ready, а не только о Project Completed) — не блокирует текущий документ, отмечаю в Backlog.
