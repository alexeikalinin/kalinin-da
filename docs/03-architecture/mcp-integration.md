# MCP Integration

Статус: Draft v0.1 — на ревью
Назначение: описать, каким конкретно техническим способом инструмент из реестра ([[Tool-Integration]]) физически подключается к агенту — через протокол MCP (Model Context Protocol, см. [[Glossary]]).

Простыми словами: Tool Integration — это "список того, чем сотруднику разрешено пользоваться" (рекламный кабинет, поиск в интернете и т.д.). MCP — это "розетка", через которую сотрудник физически подключается к этому инструменту, и правила, по которым эта розетка работает одинаково для любого инструмента — не нужно каждый раз изобретать новый способ подключения под каждый новый сервис. Вы уже видите MCP на практике в этой самой рабочей среде — Supabase, Vercel и другие инструменты подключены сюда именно через MCP.

Использует термины из [[Glossary]]. Детализирует протокол для [[Tool-Integration]]. Опирается на [[Architecture-Overview]] (ADR-0001 — стек Vercel + Supabase).

---

## Purpose

Зафиксировать, что MCP — единый и единственный способ, которым агенты получают доступ к инструментам, чтобы не возникало исключений ("для этого сервиса подключаемся напрямую, в обход реестра") — что подорвало бы принцип контролируемого доступа из Tool Integration.

## Scope

Документ описывает: что такое MCP-сервер в контексте платформы, как реестр инструментов (Tool Integration) связан с MCP-серверами, как обеспечивается тенант-специфичный доступ через один и тот же MCP-сервер. Не описывает: реализацию конкретных MCP-серверов (это Этап 2), низкоуровневый формат протокола (это готовый стандарт, не наше архитектурное решение).

---

## 1. Что такое MCP-сервер простыми словами

MCP-сервер — это "переводчик" между агентом и конкретным внешним сервисом (например, Google Ads). Агенту не нужно знать, как именно устроено API Google Ads — он обращается к MCP-серверу единым, стандартным образом, а MCP-сервер уже сам переводит это в специфичные вызовы конкретного сервиса. Это работает одинаково для любого инструмента — будь то рекламный кабинет, база данных или поиск в интернете.

## 2. Связь с реестром инструментов (Tool Integration)

Каждая запись в реестре разрешённых Tool (Tool Integration, раздел 1, требует утверждения при добавлении нового типа — решение от 2026-08-04) соответствует одному подключённому MCP-серверу. Когда вы утверждаете новый тип инструмента — это технически означает подключение нового MCP-сервера к платформе. Один MCP-сервер может предоставлять сразу несколько связанных возможностей (например, MCP-сервер Supabase даёт доступ и к базе данных, и к её структуре) — агенту доступны только те возможности, которые прямо перечислены в его роли (Agent Framework, "Используемые инструменты"), даже если MCP-сервер технически умеет больше.

## 3. Тенант-специфичный доступ через общий MCP-сервер

Один и тот же MCP-сервер (например, "коннектор к Google Ads") используется для разных клиентов — но при каждом вызове передаются учётные данные именно того тенанта, чей Project сейчас исполняется (см. Tool Integration, раздел 3). MCP-сервер не хранит "какой клиент сейчас работает" сам по себе — эту информацию обязан передавать Workflow Engine/AgentRuntime при каждом вызове, опираясь на то, к какому Project и тенанту относится текущая Task.

**Уточнено по итогам независимого технического ревью (см. Queue, раздел 5):** учётные данные не передаются агенту заранее и не кешируются на стороне воркера между вызовами — они запрашиваются заново на каждый отдельный MCP-вызов, по `tenant_id` из неизменяемого контекста исполнения текущей Task. Это устраняет путь, которым устаревшие или чужие учётные данные могли бы "прилипнуть" к переиспользуемому воркеру при горизонтальном масштабировании (несколько экземпляров одной роли одновременно).

## 4. Ошибки на уровне MCP

MCP-вызов может завершиться ошибкой (сервис недоступен, невалидные учётные данные, лимит запросов исчерпан). Это ровно тот случай "инструмент подвёл", который уже описан в Tool Integration (раздел 4) — MCP не вводит отдельный протокол ошибок, а использует общий: retry в разумных пределах → Failed → решает Workflow Engine/Recovery.

## 5. Почему это не блокирует расширяемость (снова NFR-10)

Добавление нового инструмента = добавление нового MCP-сервера + запись в реестре после вашего утверждения. Ни Agent Framework, ни Workflow Engine, ни другие агенты не меняются — они продолжают обращаться к инструментам единым образом через MCP, независимо от того, сколько всего MCP-серверов подключено.
