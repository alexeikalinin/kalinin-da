# Reflection System

Статус: Draft v0.1 — на ревью
Назначение: описать сам процесс "разбора полётов" после завершения Project — как система анализирует, что получилось, что нет, и превращает это в "уроки" для [[Learning-System]].

Простыми словами: если Learning System — это "как агент использует опыт", то Reflection System — это "как вообще появляется этот опыт". Представьте планёрку в конце проекта: что сработало, что нет, где потратили лишнее время, какие инструменты подвели. Reflection — это такая планёрка, только не для людей, а автоматическая, происходящая после каждого Project.

Использует термины из [[Glossary]]. Реализует [[Functional-Requirements]] (FR-14). Потребляет события из [[Events]] (Project Completed) и логи из будущего документа Logging/Audit. Поставляет "уроки" в [[Learning-System]] (структура "урока" уже определена там).

---

## Purpose

Зафиксировать, что именно анализируется после Project, кто/что это делает, и как результат анализа превращается в проверяемые "уроки", не теряя ничего важного и не создавая шума из случайных наблюдений.

## Scope

Документ описывает: что запускает Reflection, что именно анализируется (согласно директиве — успешные решения, ошибки, повторяющиеся проблемы, эффективность промптов, эффективность инструментов), как результат передаётся дальше. Не описывает: как хранится и используется результат (Learning System), как формируется сам "урок" в деталях (тоже Learning System, раздел 1).

---

## 1. Что запускает Reflection

Событие **Project Completed** (см. [[Events]]) — Reflection запускается автоматически по завершении каждого Project, независимо от Execution Tier (даже Fast-проекты дают материал для обучения, просто более скромный по объёму).

## 2. Что анализируется (по директиве)

| Что анализируется | Простыми словами | Источник данных |
|---|---|---|
| **Успешные решения** | Что сработало хорошо и стоит повторять | Logging/Audit — какие решения принял каждый агент и какой был итоговый результат (прошёл QA без доработок) |
| **Ошибки** | Что агент сделал неправильно | Task Failed / Task Needs Revision события, сопоставленные с итоговым исправлением |
| **Повторяющиеся проблемы** | Не разовая ошибка, а то, что происходит из проекта в проект | Сравнение с уже накопленными "уроками" в Learning Memory — если новое наблюдение похоже на старое, это повышает "уверенность" закономерности (Learning System, раздел 3) |
| **Эффективность промптов** | Насколько формулировка задачи агенту приводила к хорошему результату с первого раза | Сколько раз потребовалась доработка (Needs Revision) при данной формулировке Task |
| **Эффективность инструментов** | Какие Tool реально помогали, какие были бесполезны/ненадёжны | Частота ошибок/таймаутов при использовании конкретного Tool (см. Tool Integration) |
| **Предложения по улучшению** | Не просто "что было", а "что стоит поменять" | Синтез всего вышеперечисленного — формируется как кандидат в "урок" |

## 3. Кто выполняет Reflection

Не отдельная "роль" в смысле референсного конвейера маркетинговых ролей (Glossary, раздел 2) — это служебный процесс, логически похожий на Agent Architect (Agent Framework, раздел 4a): работает над данными о работе других агентов, а не над задачей клиента. Из этого следует, что Reflection подчиняется тому же общему контракту Agent Framework (вход/выход/критерии завершения), но не участвует в Workflow конкретного Project.

## 4. От анализа к "уроку" — что происходит с результатом

Reflection не пишет напрямую в Learning Memory как в готовый, подтверждённый источник — по аналогии с тем, как агент не пишет напрямую в Knowledge Base (Memory System, раздел 2):
- Обычные наблюдения (пункты из раздела 2 выше) становятся **единичными наблюдениями** в Learning Memory автоматически — это низкий риск, так как Learning System уже трактует единичные случаи осторожно (Learning System, раздел 3).
- Если Reflection выявляет что-то **значимое и системное** (например, "определённая роль постоянно проваливает QA при Fast Execution Tier" — то есть намёк на архитектурную проблему, а не просто особенность одного клиента) — это не просто становится уроком, а **дополнительно попадает в Risk Register/Backlog** (см. Dependencies) как сигнал для пересмотра самой архитектуры, а не только поведения агента.

Это разделение важно: Reflection совершенствует поведение агентов в рамках существующей архитектуры (через Learning Memory) и одновременно служит сигналом, когда проблема уже не в поведении, а в самой архитектуре (тогда это Risk Register, не Learning Memory).

## 5. Пример на референсном сценарии

После завершения Project "настроить рекламные кампании": Reflection видит, что Media Buyer Agent дважды за Project получил Needs Revision из-за нечёткого понимания бюджета. Единичный вывод: "формулировка Task для Media Buyer Agent должна явно включать бюджетные ограничения" — идёт как наблюдение в Learning Memory. Если это повторяется в третьем и четвёртом Project подряд — это уже закономерность (Learning System), и одновременно сигнал в Backlog: возможно, сама спецификация роли Media Buyer Agent (Agent Framework) неполна и должна быть пересмотрена — не просто "подучен на опыте", а исправлена в контракте.
