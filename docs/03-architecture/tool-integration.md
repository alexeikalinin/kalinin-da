# Tool Integration

Статус: Draft v0.1 — на ревью
Назначение: описать, как агенты получают доступ к внешним возможностям — поиску в интернете, чтению сайта клиента, работе с рекламными кабинетами и т.д. Отличие от Knowledge Base/Memory: там агент **читает уже собранную информацию**, здесь агент **что-то делает во внешнем мире** (Tool, см. [[Glossary]]).

Простыми словами: если Prompt Architecture — это бриф, который получает сотрудник, то Tool Integration — это список того, чем ему разрешено пользоваться на работе: у Research есть доступ в интернет, у PPC — доступ к рекламному кабинету, а у Copywriter, скорее всего, кроме текстового редактора ничего и не нужно. Никто не должен иметь доступ ко всему подряд "на всякий случай" — это и небезопасно, и не нужно для его роли.

Использует термины из [[Glossary]]. Реализует элемент "Используемые инструменты" контракта агента ([[Agent-Framework]], раздел 1). Опирается на [[Non-Functional-Requirements]] (NFR-1, NFR-14 — изоляция и авторизация). Технический протокол подключения инструментов — в следующем документе [[MCP]].

---

## Purpose

Зафиксировать принцип, по которому агент получает доступ к инструментам: не "всё доступно всем", а явный, минимально необходимый набор на роль — и как система обрабатывает ситуацию, когда инструмент подводит (недоступен, вернул ошибку).

## Scope

Документ описывает: что считается Tool, как он привязывается к роли, правило минимально необходимого доступа, обработку сбоев инструмента. Не описывает: конкретный протокол подключения (MCP — следующий документ), список всех инструментов для каждой будущей роли (это часть спецификации роли, которую пишет Agent Architect).

---

## 1. Что считается Tool

Любая внешняя возможность, которой пользуется агент для выполнения Task, кроме самой LLM (выбор модели — отдельно, Cost Optimization) и памяти (Memory System — отдельно). Примеры на referensном конвейере:

| Роль | Пример инструмента |
|---|---|
| Research Agent | Просмотр сайта клиента, поиск информации в интернете |
| SEO Agent | Проверка позиций/ключевых слов через SEO-сервис |
| PPC Agent | Работа с рекламным кабинетом Google Ads / Яндекс.Директ / VK Ads |
| Frontend Agent | Развёртывание/публикация кода (Этап 2) |
| Analytics Agent | Чтение данных из аналитической системы клиента |

## 2. Принцип минимально необходимого доступа

Каждая роль в своей спецификации (Agent Framework, раздел 1, элемент "Используемые инструменты") явно перечисляет, какие Tool ей разрешены — по умолчанию доступа нет ни к чему, кроме того, что явно указано. Пример: Copywriter Agent не имеет доступа к рекламному кабинету, даже если технически мог бы туда "дотянуться" — потому что это не его ответственность (Agent Framework, раздел 1, элемент "Ответственность"). Это не только вопрос порядка, но и безопасности: чем меньше у роли доступа, тем меньше ущерб, если что-то пойдёт не так (ошибка в промпте, неожиданное поведение модели).

## 3. Доступ к инструментам конкретного клиента (мультитенантность)

Некоторые инструменты требуют "ключей" для конкретного клиента — например, доступ к его рекламному кабинету или его аналитике. Эти ключи хранятся и используются строго в рамках изоляции тенанта (NFR-1, NFR-14) — то есть агент, работающий над Project клиента A, физически не может использовать ключ доступа клиента B, даже случайно. Это должно быть гарантировано на уровне того, как Tool получает доступ к учётным данным, а не только на уровне "агент не должен так делать".

## 4. Что происходит, если инструмент подвёл

Соответствует протоколу ошибок из Agent Framework (раздел 4): если Tool недоступен, вернул ошибку или дал неожиданный результат — это не заставляет весь Project падать. Агент возвращает статус в зависимости от серьёзности:
- если задачу можно выполнить без этого конкретного вызова (например, повторной попытки достаточно) — агент пробует снова в разумных пределах;
- если инструмент критичен и недоступен — Task помечается как Failed, и дальше решает Workflow Engine/Recovery (см. Workflow Engine, раздел 4-5), а не сам инструмент.

Каждый такой случай фиксируется в Logging/Audit — это то, что позже Reflection использует для оценки "эффективности инструментов" (Reflection System, раздел 2): если конкретный Tool систематически подводит, это сигнал для пересмотра, а не просто разовая случайность.

## 5. Инструменты и Execution Tier

По аналогии с промптами (Prompt Architecture, раздел 2): на Fast-уровне агент может использовать более быстрые/дешёвые варианты инструмента (например, поверхностный поиск вместо глубокого обхода сайта), на Standard — более тщательные. Конкретная реализация этого выбора — деталь спецификации роли, здесь фиксируется только сам принцип.

## Open Questions

1. ~~Реестр доступных инструментов.~~ Решено (2026-08-04): ведётся центральный реестр разрешённых Tool; подключение нового инструмента в реестр требует вашего явного подтверждения — по той же логике, что и активация новой роли (Agent Framework, раздел 4a). Подключение нового клиента к уже одобренному типу инструмента (например, ещё один аккаунт Google Ads) не требует повторного утверждения самого инструмента — только выдачи ключа доступа этому тенанту (раздел 3).
2. **Хранение и ротация ключей доступа клиентов (раздел 3).** Технический механизм — предлагаю закрыть в Security, не здесь.
