# Product Specification

Статус: Draft v0.1 — на ревью
Назначение: описать продукт с точки зрения пользователя — что он вводит, что получает, какие сценарии использования существуют для каждого сегмента. Отвечает на вопрос «что видит и делает пользователь», в отличие от Business Goals («зачем это выгодно») и Architecture («как это устроено внутри»).

Использует термины из [[Glossary]]. Зависит от [[Vision]] и [[Business-Goals]] (сегменты Owner / White-label Specialist / White-label Agency, двухконтурная модель).

---

## Purpose

Зафиксировать пользовательские сценарии и границы продукта настолько конкретно, чтобы из документа можно было однозначно вывести Functional Requirements — без домысливания на следующем этапе.

## Scope

Документ описывает: вход/выход системы с точки зрения пользователя, ключевые пользовательские сценарии (user journeys) для каждого сегмента, точки Human-in-the-loop, границы того, что продукт делает и не делает на первой итерации.

Документ не описывает: конкретный UI/UX (это Этап 2, после утверждения документации — на Этапе 1 допустимы только концептуальные схемы взаимодействия), внутреннее устройство агентов (Agent Framework), схему данных (Database).

## 1. Вход и выход системы (общий контракт)

**Вход (Project Input):**
- URL сайта;
- описание бизнеса;
- продукт/услуга;
- маркетинговая задача (свободная формулировка).

**Выход (Project Output):**
- готовый комплект маркетинговых материалов, состав которого определяется задачей и планом, построенным Project Manager Agent (см. Glossary, раздел 2);
- отчёт о проделанной работе (Report Generator Agent) — включает, как минимум, какие Agent участвовали, какие решения приняты, какие метрики/результаты достигнуты.

Это единый контракт для обоих контуров (Owner и White Label) — различие между ними не в контракте, а в том, кто инициирует Project и в каком бренд-контексте выдаётся результат (см. раздел 3).

## 2. Пользовательские сценарии (User Journeys)

### 2.1. Сценарий Owner (Контур A)

1. Владелец (Kalinin Digital Agency) создаёт Project для конкретного клиента агентства, указывая вход (раздел 1).
2. Платформа декомпозирует задачу, запускает нужных Agent по Workflow.
3. Владелец может (не обязан) отслеживать прогресс выполнения Project в реальном времени.
4. По завершении владелец получает Project Output и отчёт.
5. При необходимости владелец инициирует доработку — это порождает новую Task в рамках того же Project, а не новый Project (переиспользуется Project Memory).

### 2.2. Сценарий White-label Specialist / Agency (Контур B)

Совпадает с 2.1 с двумя отличиями:
- взаимодействие происходит под брендом специалиста/агентства (white-label), конечный клиент специалиста не видит платформу напрямую;
- доступ специалиста/агентства ограничен их собственными Project (мультитенантная изоляция — см. Business Goals, раздел 1).

Для Agency (в отличие от одиночного Specialist) сценарий дополнительно включает управление несколькими пользователями внутри организации и распределение Project между ними — это отмечено как открытый вопрос ниже, так как требует решения по ролевой модели доступа.

### 2.3. Точки Human-in-the-loop

По умолчанию (в соответствии с Vision — «минимальное вмешательство») человек участвует в двух точках:
- **постановка задачи** — на входе Project;
- **приёмка результата** — на выходе Project, с возможностью запросить доработку.

Открытый вопрос: нужны ли промежуточные точки подтверждения внутри Workflow (например, утверждение стратегии до начала генерации материалов) — см. раздел «Open Questions».

## 3. Границы продукта на первой итерации

Соответствует принципу «референсный сценарий вместо проектирования под сотни агентов сразу» (Vision, раздел 3; Business Goals, веха года 1):

**Входит в первую итерацию:**
- Контур A (Owner) как основной сценарий валидации;
- referensный конвейер ролей (Glossary, раздел 2) как первый рабочий Workflow;
- мультитенантная изоляция данных заложена в архитектуру (Business Goals, раздел 1), но White-label UX может быть минимальным на первой итерации.

**Не входит в первую итерацию (переносится в Backlog):**
- полноценное управление пользователями внутри White-label Agency (роли, права доступа второго уровня);
- биллинг/квоты для White Label (зависит от нерешённого вопроса юнит-экономики, Business Goals, Open Questions п.2);
- расширение библиотеки ролей за пределы референсного конвейера.

## 4. Что продукт не делает (явные не-цели)

- Продукт не заменяет прямое взаимодействие человека с конечным клиентом — он производит материалы и отчёты, но не ведёт коммуникацию с конечным клиентом от своего имени (если это не будет явно определено отдельной ролью в будущем).
- Продукт не гарантирует конкретные маркетинговые результаты (например, рост конверсии на X%) — гарантируется процесс и качество выполнения, а не бизнес-результат клиента.

## Open Questions

1. ~~Промежуточные точки Human-in-the-loop.~~ Решено: настраиваемо на уровне Project — пользователь при создании Project выбирает уровень контроля (только выход / промежуточное подтверждение стратегии). Это функциональное требование — конфигурируемый Approval Level, переносится в Functional Requirements.
2. **Ролевая модель внутри White-label Agency.** Остаётся открытым, отложено до `Non-Functional Requirements`/`Security` — не блокирует Functional Requirements.
3. ~~Формат отслеживания прогресса.~~ Решено: нужен просматриваемый статус прогресса Project (не обязательно push/realtime-канал — допустимо периодическое обновление статуса) плюс обязательное уведомление по завершении. Переносится в Functional Requirements как отдельная функция; конкретный технический механизм (poll vs push) — вопрос Non-Functional Requirements/Events.
