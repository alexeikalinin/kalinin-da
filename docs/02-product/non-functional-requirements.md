# Non-Functional Requirements

Статус: Draft v0.1 — на ревью
Назначение: зафиксировать качественные атрибуты системы (изоляция, скорость, надёжность, масштаб, стоимость), которые не выражаются как отдельная функция, но ограничивают и направляют все последующие Architecture-документы. Отвечает на вопрос «насколько быстро/надёжно/безопасно/дёшево», в отличие от Functional Requirements («что система умеет»).

Использует термины из [[Glossary]]. Каждое требование помечено идентификатором (NFR-N). Зависит от решений в [[Functional-Requirements]], [[Business-Goals]], [[Product-Specification]].

---

## Purpose

Дать Architecture Overview и последующим документам раздела 03 конкретные, обоснованные бизнес-решением ограничения — так, чтобы выбор технологий (durable workflow engine, схема БД, механизм realtime-обновлений) делался по зафиксированным требованиям, а не по умолчанию инструмента.

## Scope

Документ описывает: изоляцию данных, требования к скорости выполнения Project (Execution Tier), отказоустойчивость/Recovery, наблюдаемость прогресса, масштабируемость (горизонт 5 лет / сотни ролей), стоимостные ограничения. Не описывает конкретные технологии — это Architecture Overview.

---

## 1. Мультитенантность и изоляция данных

**NFR-1. Уровень изоляции.** Логическая изоляция — общая база данных с обязательным row-level security (или эквивалентным механизмом) на уровне каждого тенанта (решение от 2026-08-04). Причина выбора: соответствует уровню риска первой итерации (Owner + ограниченный White Label), дешевле и быстрее физической изоляции; пересмотр в сторону физической изоляции возможен point-in-time для отдельных enterprise-тенантов в будущем без переписывания ядра, если схема БД проектируется с tenant_id как обязательным полем с самого начала (переносится как обязательное требование в Database).

**NFR-2. Полнота изоляции.** Изоляции подлежат: Project, Task Memory, Project Memory, Company Memory, Project Output, логи (Logging/Audit). Knowledge Base общего домена (не привязанная к конкретному клиенту) может быть общей между тенантами — граница между «общим знанием» и «данными клиента» уточняется в Knowledge Base (Architecture).

## 2. Скорость выполнения (Execution Tier)

Соответствует FR-2a.

**NFR-3. Целевые ориентиры по уровням** (ориентировочные, уточняются во время реализации, не являются SLA-обязательством перед конечным клиентом):
- *Fast* — единицы–десятки минут на Project.
- *Standard* — часы (в пределах одного рабочего дня) на Project.

**NFR-4. Расширяемость справочника уровней.** Workflow Engine и очереди (Queue) должны поддерживать добавление нового Execution Tier (например, будущего *Deep*) как конфигурацию (веса/лимиты итераций на роль), а не как отдельную ветку кода.

**NFR-5. Параллелизм.** Fast-уровень требует, чтобы независимые по Workflow-графу Task (например, SEO и PPC, не зависящие друг от друга) исполнялись параллельно, а не последовательно — иначе ориентир «минуты» недостижим при 13 ролях референсного конвейера.

## 3. Надёжность и Recovery

**NFR-6. Восстановимость.** Любой Project должен быть восстановим после сбоя платформы без потери уже выполненной работы — состояние Task и Workflow обязано быть персистентным (durable), не храниться только в памяти процесса (прямое следствие FR-13 и принципа Recovery из Vision).

**NFR-7. Полнота аудита.** Logging/Audit должен обеспечивать возможность полностью восстановить историю выполнения любого Project (кто, что, когда, с каким результатом) — без пробелов, так как это единственный источник данных для Recovery и Reflection.

## 4. Наблюдаемость прогресса

Соответствует FR-3, FR-4.

**NFR-8. Механизм обновления статуса.** Достаточен periodic pull (пользователь открывает статус Project и видит актуальное состояние) — постоянный push-канал (WebSocket/SSE) не обязателен на первой итерации (Product Specification, решение от 2026-08-04: «желательно посмотреть прогресс» — не сформулировано как жёсткое требование к мгновенности). Решение упрощает Events/Architecture на первой итерации; пересмотр — открытый вопрос ниже.

**NFR-9. Надёжность уведомления о завершении.** Уведомление о завершении Project должно быть гарантированно доставлено (at-least-once) — потеря уведомления о готовом результате недопустима независимо от Execution Tier.

**Временное отступление (2026-08-04, см. [[API-Application-Layer]] раздел 4):** до подключения канала доставки (Telegram-бот) проактивная доставка не реализована — статус доступен только при просмотре прогресса (periodic pull, NFR-8). Это сознательное, явно зафиксированное временное ослабление именно этого требования на период до интеграции канала, а не отмена NFR-9.

## 5. Масштабируемость (горизонт 5 лет, Business Goals)

**NFR-10. Расширяемость ролей.** Добавление новой роли (Agent) не должно требовать изменения контракта Agent Framework, Workflow Engine или схемы Memory — только регистрации нового Agent по существующему контракту (прямое архитектурное следствие цели «сотни ролей без переписывания ядра»).

**NFR-11. Горизонтальный масштаб исполнения.** Архитектура должна допускать увеличение числа одновременно исполняемых Project и Task горизонтальным добавлением вычислительных ресурсов, без структурных изменений Workflow Engine.

## 6. Стоимость

**NFR-12. Прогнозируемость стоимости.** Стоимость выполнения одного Project должна быть оценима до начала исполнения (хотя бы приблизительно, на основе Execution Tier и состава ролей) — необходимо для будущего биллинга White Label (Business Goals, Open Question п.2) и для решений Cost Optimization (FR-15).

**NFR-13. Соответствие Execution Tier и стоимости.** Fast-уровень обязан использовать модели с более низкой стоимостью/задержкой там, где качество остаётся приемлемым; Standard допускает более дорогие модели там, где это оправдано глубиной задачи (Cost Optimization, Business Goals раздел 4).

## 7. Безопасность (базовый уровень, детализация — отдельный документ Security)

**NFR-14. Аутентификация и авторизация тенанта.** Любой доступ к Project/Task/Memory обязан быть привязан к аутентифицированному тенанту — без анонимного доступа к данным другого тенанта ни при каких условиях (жёсткое требование, не подлежит смягчению ради простоты реализации).

## Open Questions

1. **Пересмотр NFR-8 (pull vs push) при росте Standard/Deep-проектов.** Для многочасовых Project periodic pull может оказаться неудобным даже без формального SLA на мгновенность — решение о push-канале предлагаю принять на Architecture Overview с учётом реальной стоимости реализации, не блокируя этот документ.
2. **Конкретные числа NFR-3 (минуты/часы).** Зафиксированы как ориентиры, не как проверяемые SLA. Нужно ли переводить их в жёсткие SLA-обязательства для White Label клиентов — зависит от нерешённого вопроса юнит-экономики (Business Goals, Open Question п.2).
3. **Ролевая модель White-label Agency (перенесено из Product Specification, Open Question п.2).** NFR-1/NFR-2 покрывают изоляцию между тенантами, но не разграничение прав внутри одного тенанта (несколько пользователей одной Agency). Остаётся открытым, предлагаю закрыть на Security.
