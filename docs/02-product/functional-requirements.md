# Functional Requirements

Статус: Draft v0.1 — на ревью
Назначение: перевести пользовательские сценарии из [[Product-Specification]] в конкретные, проверяемые функции системы. Отвечает на вопрос «что система должна уметь», в отличие от Product Specification («что видит пользователь») и Non-Functional Requirements («насколько быстро/надёжно/дёшево»).

Использует термины из [[Glossary]]. Каждое требование помечено идентификатором (FR-N) для трассируемости из будущих Architecture-документов и Testing.

---

## Purpose

Дать однозначный, проверяемый список функций, достаточный для того, чтобы Architecture Overview и Agent Framework могли проектироваться без домысливания недостающих сценариев.

## Scope

Документ описывает функции уровня платформы (создание Project, управление Approval Level, отслеживание прогресса, получение результата) и функции уровня агентной системы (то, что обязан уметь любой Agent независимо от роли). Не описывает: конкретные алгоритмы/модели (Architecture), конкретные роли сверх референсного конвейера (Glossary), UI-реализацию (Этап 2).

## 1. Управление Project

**FR-1. Создание Project.** Пользователь (Owner или White-label Specialist/Agency) создаёт Project, указывая: URL сайта, описание бизнеса, продукт, маркетинговую задачу (Product Specification, раздел 1).

**FR-2. Выбор Approval Level.** При создании Project пользователь настраивает уровень контроля:
- *Output-only* — подтверждение только на выходе Project;
- *Strategy-gate* — дополнительное обязательное подтверждение стратегии/плана (сформированного PM Agent) до начала исполнения дорогостоящих Task.
Значение по умолчанию — **Strategy-gate** (решение от 2026-08-04).

**FR-2a. Выбор Execution Tier.** При создании Project пользователь выбирает уровень скорости/глубины выполнения из расширяемого справочника уровней. На первой итерации поддерживаются:
- *Fast* — минимальная глубина Research и самопроверки, минуты на Project — сценарий быстрого черновика для менее приоритетного клиента;
- *Standard* — полноценный Research, внутренние итерации самопроверки/доработки до QA, часы на Project — сценарий для приоритетного клиента (решение от 2026-08-04).
Справочник уровней проектируется расширяемым (Architecture Overview) — добавление уровня *Deep* (дни, многораундовый QA) в будущем не должно требовать пересмотра ядра Workflow Engine, но не входит в первую итерацию.

**FR-3. Отслеживание прогресса.** Пользователь может в любой момент просмотреть текущий статус Project: какие Task выполнены, какие в процессе, какие ожидают (Product Specification, решение от 2026-08-04). Механизм обновления статуса (poll/push) — вопрос Non-Functional Requirements.

**FR-4. Уведомление о завершении.** Система уведомляет пользователя по завершении Project независимо от выбранного Approval Level. *(Временно, до подключения канала доставки — реализовано как доступность статуса при просмотре прогресса, без проактивной отправки; см. NFR-9 и [[API-Application-Layer]] раздел 4.)*

**FR-5. Запрос доработки.** После получения результата пользователь может инициировать доработку в рамках того же Project — это создаёт новую Task, использующую существующую Project Memory, а не новый Project (Product Specification, раздел 2.1, п.5).

**FR-6. Получение результата.** По завершении Project пользователь получает Project Output (комплект материалов) и отчёт от Report Generator Agent, включающий как минимум: участвовавших Agent, ключевые решения, метрики/результаты (Product Specification, раздел 1).

## 2. Мультитенантность и брендирование (обязательны с первой итерации — Business Goals, раздел 1)

**FR-7. Изоляция данных между тенантами.** Project, Project Memory и Company Memory одного тенанта (Owner или White-label клиента) не должны быть доступны другому тенанту.

**FR-8. Брендированный вывод.** Для Контура B (White Label) Project Output и уведомления должны поддерживать оформление под бренд специалиста/агентства, без прямого упоминания платформы (Product Specification, раздел 2.2).

## 3. Функции агентной системы (общие для любой роли)

Эти требования применимы к любому Agent независимо от специализации — являются частью контракта, детализируемого в Agent Framework.

**FR-9. Планирование.** PM Agent обязан декомпозировать Project на Task и построить Workflow до начала исполнения.

**FR-10. Исполнение специализированной Task.** Каждый Agent обязан принимать вход, определённый его ролью, и возвращать вывод в формате, пригодном для следующего Agent в Workflow или для Report Generator.

**FR-11. Контроль качества.** QA Agent обязан проверять результат перед включением в Project Output; при обнаружении проблемы — инициировать исправление силами ответственного Agent, а не пропускать проблему дальше по Workflow.

**FR-12. Журналирование действий.** Каждый Agent обязан фиксировать свои действия через Logging/Audit (см. Glossary) — без этого невозможны Recovery и Reflection.

**FR-13. Восстановление после сбоя.** Система обязана определять по логам, какой Agent выполнял работу, что завершено, и продолжать исполнение Project автоматически (Recovery, см. Vision, раздел 1).

**FR-14. Постпроектный анализ.** По завершении Project система обязана инициировать Reflection и пополнять Learning Memory (Glossary).

**FR-15. Выбор модели по задаче.** Система обязана выбирать конкретную LLM для каждой Task на основе стоимости/качества/скорости/сложности, а не использовать одну модель для всех задач (Cost Optimization, см. директиву и Business Goals раздел 4).

## 4. Границы (соответствие Product Specification, раздел 3)

Явно не входят в функциональные требования первой итерации (перенесены в Backlog):
- управление пользователями и правами доступа внутри White-label Agency сверх базовой мультитенантной изоляции (FR-7);
- биллинг и квоты для White Label;
- функции сверх референсного конвейера ролей.
