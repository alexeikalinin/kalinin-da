# Client DataLens Dashboard Playbook

Статус: v1.0 — практическая инструкция, основана на реальном опыте (Медавеню, 2026-08-18…19)
Назначение: пошаговая схема для подключения нового клиента к отчётности через DataLens + `ad_stat`, без повторного наступания на уже пройденные грабли.

Использует термины из [[Glossary]]. Дополняет [[Client-Ad-Account-Access-Model]], [[Tool-Integration]].

---

## 0. Перед тем как начинать — вопросы клиенту/пользователю

Не приступать к шагу 1, пока не получены ответы на всё ниже. Ошибка в этом шаге стоит дороже всего — она тихо искажает все графики и обнаруживается не сразу.

1. **Какие цели/конверсии считать целевыми** — отдельно по каждой площадке (Google Ads Conversion Actions, Яндекс.Метрика Цели). Клиентские кабинеты почти всегда содержат лишние/тестовые/дублирующиеся цели (см. пример ниже) — нельзя просто взять "все конверсии из кабинета".
2. **Есть ли у клиента свои рекламные аккаунты** или заводим агентские — см. [[feedback-client-onboarding-ask-existing-accounts]].
3. **Какой путь доступа использовать** — агентский MCC/логин, прямой доступ на агентском логине, или отдельный личный логин — см. [[feedback-client-onboarding-ask-access-path]].
4. **В какой валюте отчитываться по каждой площадке** — не предполагать, спросить/проверить через API (`customer.currency_code` в Google Ads, `Currency` в Яндекс.Директ `agencyclients`/`clients`). Разные площадки почти всегда в разных валютах — см. §3.
5. **Нужен ли публичный share-доступ к дашборду** — по умолчанию НЕ включать без явного запроса (см. Backlog, решение от 2026-08-19).

**Пример вопроса клиенту про конверсии** (реальный кейс Медавеню — Google Ads Conversion Actions содержали одновременно старую и новую версию одной и той же конверсии с `primary_for_goal: true`, что даёт двойной счёт; и минимум одну полностью сломанную конверсию с 0 срабатываний за 30 дней, но всё ещё активную): не подключать конверсии автоматически по признаку "активна в кабинете" — выгрузить полный список с именами и попросить владельца аккаунта/маркетолога клиента явно отметить нужные.

## 1. Схема данных (один раз на всю систему, не per-client)

Единая fact-таблица `ad_stat` в Supabase (см. `supabase/migrations/0002_client_ad_accounts.sql`, `0005_ad_stat_currency.sql`) — все клиенты пишут в одну таблицу, разделены по `client_id`/`tenant_id`. DataLens подключается к ней **один раз** через нативный Postgres-коннектор — новые клиенты не требуют новой настройки коннектора/датасета, только новых чартов/дашборда.

Колонки, важные для отчётности: `platform`, `account_id`, `date`, `campaign_id`, `campaign_name`, `impressions`, `clicks`, `cost`, `currency`, `conversions` (jsonb, по одному значению на цель), `conversions_total` (посчитанная сумма всех подключённых целей — см. §0.1, считается на этапе синка, не в DataLens).

## 2. Подключение нового клиента к данным (код, не DataLens)

1. `platform_identity` + `client_ad_account` в Supabase — см. [[client-ad-account-access-model]].
2. Одобренный список `target_conversion` на клиента и платформу — из §0.1, сохранить в Supabase, не только в памяти сессии.
3. Прогнать `syncAdStats` (`apps/web/lib/sync-ad-stats.ts`) за нужный период. Функция сама подтягивает валюту аккаунта через `getAccountCurrency` (`google-ads.ts`/`yandex-direct.ts`) и считает `conversions_total` по одобренному списку целей.
4. Свериться SQL-запросом с реальными цифрами в кабинетах за 2-3 дня, прежде чем идти в DataLens — дешевле поймать ошибку синка на этом шаге, чем потом гонять баг через 9 чартов.

## 3. Валюта — не предполагать, проверять

Разные рекламные системы почти всегда выставлены в разных валютах для одного и того же клиента (реальный кейс: Медавеню — Google Ads в USD, Яндекс.Директ в BYN). Если это не учесть:
- расход/CPA разных площадок нельзя складывать или показывать на одной оси без явного указания валюты в заголовке/фильтре;
- график "и то и то на одном полотне" по деньгам без разделения по `currency` — гарантированная ошибка, которую пользователь заметит сразу же ("расход выглядит одинаково").

**Правило**: денежные метрики (расход, CPA) всегда либо (а) отдельный чарт на каждую платформу/валюту с валютой в заголовке, либо (б) единый чарт с обязательным фильтром/селектором по платформе, который гарантированно не даёт смешать валюты по умолчанию (см. §5.3 про селекторы).

## 4. Датасет и коннектор в DataLens (код есть, ручной шаг остаётся)

Используй `createPostgresConnection` и `createAdStatDataset` из `apps/web/lib/tools/datalens.ts` — уже реализовано и переиспользуемо. Дважды сверься с [[reference-datalens-gotchas]] перед запуском:

- Хост подключения — **Session Pooler**, не прямой (готча #1).
- CA-сертификат Supabase прикрепляется **вручную** через UI после создания коннекции (готча #2) — единственный шаг, который код не автоматизирует.
- В названиях датасета/чартов/дашборда — никаких `/` (готча #3).
- `createDataset` — обязательно с явным `raw_schema`, не полагаться на автоинтроспекцию (готча #4).

Расчётные поля (CTR/CR/CPA) создавай **плоским делением**, никогда не `DIV_SAFE(...)` или `NULLIF(...)` как внешней функцией — это ломает классификацию поля (готчи #6, #10). Рабочие формулы:

```
CTR, %  = SUM([clicks]) * 100.0 / SUM([impressions])
CR, %   = SUM([conversions_total]) * 100.0 / SUM([clicks])
CPA     = SUM([cost]) / SUM([conversions_total])
```

Если поле группируется по измерению, где возможен ноль в знаменателе (например CPA в разрезе кампаний по дням — у кампании легко может быть 0 конверсий в конкретный день), используй защищённый вариант **с обязательной внешней обёрткой**, иначе поле опять неправильно классифицируется:

```
CPA (с защитой от деления на 0) = DIV_SAFE(SUM([cost]), SUM([conversions_total])) + 0
```

## 5. Чарты и дашборд

### 5.1 Порядок построения
Строй чарты в отдельной вкладке (не в дашборде), сохраняй, потом добавляй на дашборд через кнопку "Чарт" → "Выбрать" — так проще проверить данные до того, как они попадут перед глазами клиента.

### 5.2 Таблица "Table" — не забыть агрегацию
Если строишь `Таблица` (например "Конверсии/CPA по кампаниям"): по умолчанию каждый добавленный показатель имеет агрегацию "Нет", и таблица покажет данные построчно (по дате), а не сгруппированными по измерению. **Явно выставь "Сумма" на каждый показатель** через диалог поля (готча #9) — иначе получишь сотни строк вместо одной на кампанию.

### 5.3 Дашбордовые селекторы — проверяй связи, не только сохраняй
Если добавляешь "Селектор" (например переключатель платформы для drill-down по кампаниям) — **он автоматически привязывается ко ВСЕМ чартам на дашборде**, использующим то же поле того же датасета, включая чарты, созданные задолго до селектора и уже имеющие свой фильтр (готча #13). Это не безобидная фича, а источник тихой порчи данных на всём дашборде.

Обязательный чек-лист после добавления любого селектора:
1. Открой "Связи" — третья иконка на виджете селектора (после закрепить/шестерёнка), не первая.
2. Пройдись по каждой строке со связью "Исходящая".
3. Для каждого чарта, который НЕ должен управляться этим селектором — переключи связь на "Не связаны".
4. Переключи селектор между значениями и визуально убедись, что несвязанные чарты не изменились.

### 5.4 Раскладка — не оставляй всё в один столбец
После добавления чартов на дашборд они по умолчанию идут одной колонкой вниз, даже если справа много свободного места. Перетаскивай заголовки чартов в соседние колонки, чтобы получить сетку (обычно 2-3 в ряд для клиентского дашборда шириной ~1500px). Drag-and-drop может неожиданно сдвигать соседние виджеты на другую строку — после каждого перетаскивания делай полный скриншот, чтобы подтвердить фактический результат, прежде чем продолжать (готча #14).

## 6. Финальная проверка перед показом клиенту

- [ ] Каждая денежная метрика подписана валютой в заголовке или явно отфильтрована по платформе.
- [ ] Сверил хотя бы 2-3 значения (расход, клики) на графике с реальными цифрами в кабинете клиента за конкретный день.
- [ ] Если есть селектор — проверил связи (§5.3) и переключил его между всеми значениями визуально.
- [ ] Таблицы с группировкой показывают одну строку на измерение, а не сотни строк (§5.2).
- [ ] Публичный доступ не включён, если явно не запрошен.
- [ ] Одобренный список целевых конверсий сохранён в памяти/Supabase, а не только "в переписке" — следующий человек должен найти его без переспроса клиента.
