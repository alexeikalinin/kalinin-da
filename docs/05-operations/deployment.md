# Deployment

Статус: Draft v0.1 — на ревью
Назначение: описать, как и куда разворачивается платформа на Этапе 2, и какие условия обязаны быть выполнены прежде, чем что-либо реально запускается — особенно для внешних (White-label) пользователей.

Простыми словами: это правило "когда можно открывать двери агентства для клиентов", а не просто "как поставить сервер".

Использует термины из [[Glossary]]. Опирается на [[Architecture-Overview]] (ADR-0001), [[Testing]], [[Security]] (в т.ч. риск локализации персональных данных, раздел 7).

---

## Purpose

Зафиксировать окружения развёртывания и обязательные условия ("ворота") перед переходом от одного окружения к другому — чтобы запуск не был "молчаливым" решением в моменте, а опирался на явный чек-лист.

## Scope

Документ описывает окружения (development/staging/production), условия перехода между ними, и явно выделяет разницу между "запуск для Owner" и "запуск для White-label клиентов" — так как второе несёт значительно больше юридических и репутационных рисков. Не описывает: технические шаги CI/CD (инженерная деталь Этапа 2).

---

## 1. Окружения

| Окружение | Назначение | Кто использует |
|---|---|---|
| Development | Разработка и ручная проверка | Только вы / тот, кто пишет код |
| Staging | Прогон референсного сценария и тестов из Testing перед реальным использованием | Вы, для приёмки |
| Production (Owner) | Реальная работа над Project для клиентов Kalinin Digital Agency (Контур A) | Владелец |
| Production (White Label) | Реальная работа для внешних специалистов/агентств (Контур B) | White-label клиенты |

## 2. Условия перехода ("ворота")

**Development → Staging:** код проходит уровни тестирования "Контракт роли" и "Workflow целиком" (Testing, раздел 1).

**Staging → Production (Owner):** дополнительно проходят тесты "Recovery" и "Изоляция между тенантами" (даже если тенант пока один — Owner) — а также успешный ручной прогон полного референсного сценария (Business Goals, веха года 1) с вашей приёмкой результата.

**Production (Owner) → Production (White Label):** отдельные, более строгие условия, так как здесь впервые появляются реальные внешние пользователи и потенциально персональные данные из разных юрисдикций:
- все уровни тестирования из Testing пройдены, включая "Изоляция между тенантами" с более чем одним реальным тенантом;
- **риск локализации персональных данных (Security, раздел 7) явно разрешён.** Основной поток (лиды с лендингов) уже закрыт архитектурно — RISK-03a: отдельная система хранения лидов в РБ, вне стека платформы. Условие для этого перехода — явное решение по остаточному RISK-03b (Research Agent и данные третьих лиц с существующего сайта клиента): либо принят технический контроль, либо осознанно подтверждено, что он остаётся допустимым риском именно для тех White-label клиентов, которых вы подключаете. Это жёсткое условие: White Label с клиентами из РБ/РФ не открывается без явного решения по RISK-03b, даже если оно — "принимаем как есть".

## 3. Почему это разделено на два "production", а не один

Прямое следствие двухконтурной модели (Business Goals, раздел 1): риски и требования готовности для Owner и для White Label разные по степени строгости, и запуск для одного не должен автоматически означать готовность для другого.
