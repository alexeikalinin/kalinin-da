# Resend — верификация домена и прогрев отправки

Статус: Operational — написано 2026-08-30 вместе с
`apps/web/lib/tools/email-provider.ts` (Track A, outreach-отправка).

Назначение: ручные шаги, которые должен выполнить владелец агентства,
прежде чем `sendOutreachEmail()` сможет реально отправлять письма. Код сам
себя блокирует, пока эти шаги не выполнены (`isSendingDomainVerified()` —
см. `email-provider.ts`), чтобы случайная отправка с плейсхолдер-домена не
испортила репутацию будущего реального домена ещё до его верификации.

---

## 1. Почему нужен отдельный поддомен, а не основная почта

Холодный outreach не должен идти с той же почты/домена, которой агентство
пользуется для переписки с реальными клиентами — жалоба на спам или
всплеск bounce от незнакомых адресов испортит репутацию домена целиком,
включая доставляемость писем реальным клиентам. Стандартная практика —
поддомен основного домена (например `mail.<агентство>.com`), не отдельная
покупка.

## 2. Шаги верификации в Resend

1. В Resend: Domains → Add Domain → указать поддомен (не корневой домен).
2. Resend сгенерирует DNS-записи (SPF, DKIM, обычно и DMARC-рекомендацию) —
   добавить их у DNS-провайдера домена вручную, один раз.
3. Дождаться статуса "Verified" в Resend (обычно от нескольких минут до
   нескольких часов на распространение DNS).
4. Установить `EMAIL_FROM_ADDRESS` (env, Vercel + `.env.local`) на реальный
   адрес с этого поддомена, например `outreach@mail.<агентство>.com`. До
   этого шага `email-provider.ts` отказывается слать реальную почту.

## 3. График прогрева (обязателен, код его не ускоряет)

Новый домен нельзя сразу грузить полным объёмом — это само по себе триггер
спам-фильтров, независимо от качества кода. Держим ограничение через
`DAILY_SEND_CAP` (env, по умолчанию 20):

| Неделя | `DAILY_SEND_CAP` |
|---|---|
| 1 | ≤20/день |
| 2 | ≤50/день |
| 3 | ≤100/день |
| 4+ | обычный режим (значение по бизнес-потребности) |

Прогрев — это смена значения env-переменной в Vercel, не изменение кода.

## 4. Что дальше не покрыто этим документом

Приём ответов адресатов (inbound parsing) требует отдельной настройки
MX-записей на том же или другом поддомене — отдельное решение от исходящей
отправки, может быть готово позже. До этого момента `reply-classifier`
работает по ручному fallback-логированию ответов (см. план Track A, §1.3).
