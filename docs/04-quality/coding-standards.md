# Coding Standards

Статус: Draft v0.1 — на ревью
Назначение: зафиксировать конвенции написания кода на Этапе 2, чтобы код разных частей системы (написанный в разное время, возможно разными людьми/AI-сессиями) выглядел и работал единообразно. Это единственный документ в пакете, который явно смотрит вперёд, на код — но сам не содержит кода, только правила.

Простыми словами: это как единый стиль оформления документов в компании — не имеет значения, кто именно написал письмо, оно должно быть узнаваемо "нашим". Для кода это работает так же: не важно, кто (или какая AI-сессия) писал конкретный файл, он должен читаться как часть одной системы.

Использует термины из [[Glossary]] — они обязательны к использованию как названия сущностей в коде (раздел 2). Опирается на [[Architecture-Overview]] (ADR-0001 — Vercel/стек).

---

## Purpose

Дать единый набор правил именования, структуры и обработки ошибок, прямо отражающих архитектурные решения, уже принятые в разделе 03 — чтобы код не "изобретал" собственный словарь понятий, отличный от документации.

## Scope

Документ описывает: язык/стек, правило именования сущностей по Glossary, соответствие протокола ошибок в коде протоколу из Agent Framework, требования к тестам (ссылка на Testing), процесс ревью кода. Не описывает: сам код, конкретные линтер-конфигурации — это инженерная деталь Этапа 2.

## Разрешено на Этапе 1: только правила и псевдокод, не production-код.

---

## 1. Язык и стек

Согласно ADR-0001 (Vercel + Supabase): TypeScript как основной язык (типизация напрямую поддерживает соответствие контрактам из Agent Framework — статус Success/Needs Revision/Failed должен быть типом, а не строкой "на удачу"), Next.js/Vercel как платформа исполнения, Supabase-клиент для доступа к данным.

## 2. Именование сущностей — обязательное соответствие Glossary

Ключевое правило: **термины из Glossary — это не просто документационные слова, а обязательные названия в коде.** Если Glossary называет сущность `Task`, в коде не должно появиться параллельного понятия `Job`/`Ticket`/`WorkItem` для того же самого — это создаёт расхождение между документацией (единственным источником истины, Glossary раздел "SSOT") и кодом.

Пример: `Project`, `Task`, `Agent`, `Workflow`, `ExecutionTier`, `ApprovalLevel` — используются в коде ровно с этими именами (или их прямым, однозначным переводом на английский, что они уже и есть).

## 3. Обработка ошибок — код отражает протокол Agent Framework

Соответствует Agent Framework, раздел 4: агент возвращает **типизированный статус** (Success / Needs Revision / Failed), а не полагается на исключения (exceptions) для ожидаемых, штатных ситуаций (например, "модель посчитала результат недостаточно хорошим" — это Needs Revision, не throw). Исключения оставлены для непредвиденных программных ошибок (баг в коде), а не для бизнес-логики, уже описанной в архитектуре.

## 4. Структура кода отражает контракт агента

Каждая роль (Agent Framework, раздел 1) реализуется как модуль, реализующий один и тот же общий интерфейс — то есть в коде должно быть буквально видно то же самое разделение "3 уникальных элемента / остальное общее", которое зафиксировано в Agent Framework. Если добавление новой роли требует правки общего интерфейса — это сигнал, что либо контракт был спроектирован неверно, либо реализация нарушает архитектуру (см. NFR-10).

## 5. Тесты — обязательны, не опциональны

Ссылается на [[Testing]]: код новой роли не считается завершённым без теста уровня "Контракт роли" (Testing, раздел 1). Код изменений в Workflow Engine/Queue/Recovery не принимается без соответствующего теста уровня "Workflow целиком"/"Recovery"/"Изоляция" — в зависимости от того, что было изменено.

## 6. Ревью кода

Любое изменение (независимо от того, кто/что его написало — вы, нанятый инженер, AI-ассистент) проходит через читаемый diff и осознанное подтверждение перед принятием — прямое продолжение принципа директивы "критичные решения не принимаются автономно", теперь уже применительно к коду, а не только к архитектуре.
