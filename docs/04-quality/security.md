## Purpose

Дать единый, непротиворечивый набор правил безопасности вместо того, чтобы решать их разрозненно в каждом документе — так как безопасность как раз тот случай, где непоследовательность между документами создаёт реальную уязвимость, а не просто архитектурную неряшливость.

## Scope

Документ описывает: аутентификацию тенанта, доступ внутри White-label Agency, хранение и передачу ключей клиентов (MCP), политику хранения логов и памяти. Не описывает: конкретные технические механизмы шифрования (реализация Этапа 2), юридические/комплаенс-требования (не подняты в директиве — открытый вопрос ниже).

## 1. Аутентификация и авторизация тенанта (реализация NFR-14)

Любое действие в системе выполняется от имени аутентифицированного тенанта. Anonymous-доступа к данным (Project, Memory, KB клиента) не существует ни при каких условиях — это жёсткое требование, уже зафиксированное в NFR-14, здесь оно не смягчается.

Технически (ADR-0001) это опирается на встроенную аутентификацию Supabase и row-level security, привязанные к `tenant_id` (Database, раздел 1).

## 2. Доступ внутри White-label Agency

Решение отложено вами сознательно (не блокирует архитектуру): на первой итерации Agency рассматривается как **один тенант с одним основным пользователем** — то есть внутренней ролевой модели (Owner/Admin/Member) пока не существует. Это не архитектурное ограничение "невозможно добавить" — а осознанное упрощение первой итерации (Product Specification, раздел 3, "не входит в первую итерацию").

Задел на будущее: так как изоляция уже строится по `tenant_id`, а не по конкретному пользователю, добавление нескольких пользователей внутри одного тенанта в будущем — это добавление уровня авторизации *внутри* тенанта, не пересмотр модели мультитенантности целиком. Перенесено в Backlog.

## 3. Хранение и передача ключей доступа клиентов (закрывает Open Question из MCP Integration)

Учётные данные клиента для внешних сервисов (например, доступ к его рекламному кабинету) хранятся:
- зашифрованными, привязанными к `tenant_id` (сущность MCP_CREDENTIAL, Database раздел 2);
- не хранятся и не кешируются на стороне MCP-сервера между вызовами (MCP Integration, раздел 3) — передаются в момент вызова;
- доступны только Task, выполняемым в рамках Project этого же тенанта — никакой агент не может обратиться к MCP_CREDENTIAL другого тенанта, даже случайно, так как выборка учётных данных всегда идёт через `tenant_id` текущей Task (то же правило row-level security, что и для остальных данных).

## 4. Политика хранения логов (закрывает Open Question из Logging/Audit)

Логи не удаляются автоматически по времени — хранятся, пока активен тенант, так как они являются единственным источником данных для Recovery (уже произошедшие Project) и Reflection (обучение на прошлом опыте). Удаление возможно только по явному запросу тенанта (например, при прекращении сотрудничества) — конкретный процесс такого удаления не архитектурное решение, а операционная процедура, вне Этапа 1.

## 5. Политика хранения Project Memory (закрывает Open Question из Database)

Симметрично логам: Project Memory не архивируется/не удаляется автоматически. Причина: и Recovery, и Learning System, и возможность запроса доработки (FR-5, "доработка через новую Task в том же Project") требуют, чтобы Project Memory оставалась доступной неопределённо долго, пока тенант активен.

## 6. Изоляция между Владельцем (Контур A) и White-label клиентами (Контур B)

Owner и White-label клиенты — разные тенанты в одной и той же системе, изолированные абсолютно так же, как два разных White-label клиента друг от друга (Business Goals, раздел 1) — Владелец не имеет особого "супер-доступа" к данным White-label клиентов, кроме случаев, явно предусмотренных договором обслуживания (вне зоны действия архитектуры — это уже юридический/договорной вопрос, не технический).

## 7. Локализация персональных данных (РБ/РФ) — критический риск, требует пересмотра перед запуском

Зафиксировано пользователем (2026-08-04): по законодательству РБ и РФ персональные данные (в контексте платформы — потенциально контакты/данные аудитории конечных клиентов, которые могут попадать в систему через Research Agent при анализе сайта/рынка) обязаны храниться физически на сервере в РБ или РФ, не за рубежом.

**Прямой конфликт с ADR-0001:** выбранный стек (Vercel + Supabase) по умолчанию размещает данные вне РБ/РФ. Это делает текущее архитектурное решение потенциально несовместимым с юридическим требованием, если персональные данные фактически попадают в систему и хранятся там.

**Варианты решения (для будущего рассмотрения, не решается в этом документе):**
1. Архитектурно не хранить персональные данные конечных клиентов в основном хранилище вообще (Research Agent анализирует, но не сохраняет ФИО/контакты как отдельные структурированные данные) — минимизирует риск, но ограничивает функциональность.
2. Выделить отдельное, физически размещённое в РБ/РФ хранилище только для персональных данных, оставив остальную архитектуру (ADR-0001) без изменений — гибридный подход.
3. Пересмотреть ADR-0001 целиком в пользу стека с хостингом в РБ/РФ (например, локальные облачные провайдеры) — самый затратный вариант, требует нового ADR.

**Уточнение и частичное решение (2026-08-04, по итогам независимого технического ревью):** основной поток персональных данных, о котором шла речь — это данные лидов (имя, телефон), оставляемые посетителями через лендинги, которые платформа помогает создавать (Frontend Agent). Решение: **сбор и хранение лидов выносится в отдельную систему** (лендинг реализуется как отдельный проект), физически размещённую на сервере в РБ — и не проходит через основной стек платформы (Vercel/Supabase, ADR-0001) вообще. Это архитектурная граница, а не обход закона: платформа AI Marketing Agency в этой части не хранит персональные данные лидов, поэтому требование локализации к её собственному хранилищу в этой части неприменимо.

**Остаточный риск (не закрыт полностью):** Research Agent, анализируя уже существующий сайт клиента (не создаваемый нами лендинг), потенциально может обнаружить и сохранить в Task/Project Memory данные конкретных людей (например, имя/email сотрудника со страницы "о компании"). Пользователь оценил это как маловероятный риск и решил не вводить технический запрет сейчас (2026-08-04) — остаётся как открытый пункт в Risk Register (RISK-03b), не блокирует Этап 1 или Этап 2.

**Статус:** частично закрыт для основного потока (лиды — через отдельную БY-систему). Остаточный риск (случайные PII в Research Agent) — открыт, низкий приоритет. Полная переоценка обоих — перед подключением White-label клиентов из юрисдикций со строгими требованиями.
