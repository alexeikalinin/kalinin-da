# Vision

Статус: Draft v0.1 — на ревью
Назначение: зафиксировать долгосрочное видение платформы (горизонт 3–5 лет), не зависящее от конкретной реализации. Это верхнеуровневый документ — детали продукта фиксируются в `Product Specification`, метрики успеха — в `Business Goals`.

Использует термины из [[Glossary]]. Не описывает, как система устроена технически (см. `03-architecture/`) — только что она должна собой представлять и зачем существует.

---

## Purpose

Определить неизменное во времени назначение платформы, которое будет служить критерием при принятии архитектурных и продуктовых решений на всех последующих этапах: если решение противоречит Vision — оно отклоняется независимо от краткосрочной выгоды.

## Scope

Документ описывает:
- то, каким становится взаимодействие пользователя с платформой в целевом состоянии;
- принцип автономности и роль человека;
- образ платформы как «цифровой компании»;
- долгосрочный принцип приоритета архитектуры и документации над кодом.

Документ не описывает: конкретные роли агентов (см. Glossary, раздел 2 — референсный конвейер), конкретные метрики (Business Goals), технологический стек (Architecture).

## 1. Формулировка видения

AI Marketing Agency — это автономная платформа, исполняющая роль полноценного маркетингового агентства, которое пользователь нанимает не как инструмент, а как исполнителя.

Целевое взаимодействие:

Пользователь предоставляет только:
- URL сайта;
- описание бизнеса;
- продукт;
- маркетинговую задачу.

Платформа самостоятельно: анализирует задачу → определяет необходимые специализации → планирует выполнение → запускает нужных Agent → организует их взаимодействие через Workflow → контролирует выполнение → проверяет качество → исправляет найденные проблемы → обучается на результатах (см. Reflection, Learning Memory) → возвращает готовый комплект материалов.

Участие человека со стороны пользователя платформы минимально — ограничивается постановкой задачи и приёмкой результата, а не участием в процессе исполнения.

## 2. Платформа как «цифровая компания»

Платформа спроектирована по аналогии с организационной структурой компании, а не как единый монолитный сервис: множество независимых Agent (Role), каждый со своей зоной ответственности, скоординированных через Workflow Engine — по аналогии с тем, как в реальном агентстве задача проходит от CEO и Project Manager к специализированным исполнителям.

Ключевое свойство: количество и состав ролей не фиксированы архитектурно. Референсный конвейер ролей (Glossary, раздел 2) — это отправная точка для проектирования Agent Framework, а не финальный или ограничивающий список. Добавление новой роли не должно требовать пересмотра ядра платформы.

## 3. Принцип долгосрочности

Целью является не создание MVP, а создание инженерной основы, способной развиваться годами без переписывания архитектуры. Из этого следует:

- решения оцениваются по долгосрочным последствиям, а не по скорости первой демонстрации;
- расширяемость (новые роли, новые модели, новые инструменты) — обязательное свойство, а не опциональное улучшение;
- на этапе проектирования (Этап 1) допустимо и приветствуется сознательное ограничение сложности первой итерации (см. Risk Register — принцип «референсный сценарий вместо проектирования под сотни агентов сразу»); это не противоречит долгосрочности, а служит проверке архитектуры на конкретном сквозном случае перед масштабированием.

## 4. Роль документации в видении платформы

Документация — не сопроводительный артефакт, а основа принятия решений (Single Source of Truth, см. Glossary). Видение считается реализованным корректно только если оно прослеживается от Vision → Product Specification → Architecture → конкретной реализации без разрывов и противоречий.
