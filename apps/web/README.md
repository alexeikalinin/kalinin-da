# @ama/web

Implements: `docs/03-architecture/api-application-layer.md` — real Next.js Route Handlers, not a skeleton anymore.

- `POST /api/projects` — FR-1/FR-2/FR-2a: create a Project (runs CEO Agent then PM Agent for real, pauses for Strategy-gate approval by default).
- `GET /api/projects` / `GET /api/projects/[id]` — FR-3: list / progress (periodic pull, NFR-8).
- `POST /api/projects/[id]/approve` — Workflow Engine §3: approves the plan and **starts a real durable Workflow DevKit run** (`lib/workflows/execute-project.ts`) — returns immediately, the graph then executes asynchronously; poll `GET /api/projects/[id]` for live progress and the terminal status.
- `POST /api/projects/[id]/reject` — rejects the plan with a comment; PM Agent rebuilds it (Workflow Engine §3).
- `GET /api/projects/[id]/output` — FR-6: the finished `ProjectOutput`, 409 until the Project is completed.
- `POST /api/projects/[id]/rework` — FR-5.

`lib/orchestrator.ts` is the one place in the codebase that knows about every role package at once — it's the real implementation of what Workflow Engine's dispatch step will eventually be. Verified end to end with real `curl` requests against `next dev` (not just unit tests): create → Strategy-gate pause → approve → all 6 Tasks execute in the correct order (PPC/Media Buyer in parallel) → real `ProjectOutput`; separately verified reject/replan and rework.

**Known simplifications, stated rather than hidden:**
- Auth is a single hardcoded Owner tenant (`lib/singletons.ts`) — API/Application Layer §1's own decision, not an oversight.
- `MemoryStore`/tool registry/event log are in-process singletons stashed on `globalThis` to survive Next.js dev's module re-evaluation — a dev convenience, not persistence. Real deployment replaces this with the Supabase-backed store the Database migration already models (`supabase/migrations/0001_init.sql`).
- Model calls go to the real Anthropic API (`lib/anthropic.ts` + `lib/real-models.ts`) when `ANTHROPIC_API_KEY` is set in `apps/web/.env.local` (gitignored, never committed); otherwise `lib/orchestrator.ts` falls back to its `fake*` callers so the app still runs without credentials (e.g. CI, a fresh clone). Verified end to end with a real `next dev` run and a real key: full graph execution through genuine Claude responses.
- Ten tools are real: `site-reader` (`lib/tools/site-reader.ts`, plain HTTP fetch, no credentials), `web-search` (`lib/tools/web-search.ts`, Perplexity `sonar`, needs `PERPLEXITY_API_KEY`), `google-ads` (`lib/tools/google-ads.ts`, Google Ads API v25 REST), `google-analytics` (`lib/tools/google-analytics.ts`, GA4 Admin API) + Google Tag Manager (`lib/tools/google-tag-manager.ts`, API v2, invoked as part of the `google-analytics` tool call), `yandex-direct` (`lib/tools/yandex-direct.ts`, Direct API v5 JSON) + `yandex-metrika` (`lib/tools/yandex-metrika.ts`, Management API, invoked as part of `google-analytics`'s multi-tool analytics call), `datalens` (`lib/tools/datalens.ts`, Yandex Cloud DataLens Public API, invoked as part of the same multi-tool analytics call), `meta-ads` (`lib/tools/meta-ads.ts`, Meta Marketing API / Graph API v21.0), and now `vk-ads` (`lib/tools/vk-ads.ts`, VK Ads API v2, `ads.vk.ru`). Google integrations share one OAuth refresh token (`lib/tools/google-oauth.ts`); Yandex Direct/Metrika share another (`lib/tools/yandex-oauth.ts`); DataLens uses a completely separate auth path (see below); Meta uses a non-expiring System User access token (see below); VK Ads uses OAuth2 Client Credentials Grant with a short-lived (~1 day) cached token (see below). All dispatched via `lib/real-tools.ts`.
  - `google-ads`/`yandex-direct`/`meta-ads`/`vk-ads` create real campaigns but always leave them paused/suspended/blocked — nothing in this system ever turns spend on — and are idempotent by campaign name so repeated runs don't create duplicates. The per-channel daily budget is a placeholder default × the model's `budgetShare`, not yet the project's real budget (`meta-ads` doesn't set a campaign-level budget at all yet — Meta budgets normally live at ad set level, which this integration doesn't create; `vk-ads` does set a placeholder `budget_limit_day` because VK requires one even on a blocked campaign).
  - `google-analytics` provisions (idempotent by project name) a dedicated GA4 Property + Web Data Stream and a GTM Container with a published GA4 Configuration tag, marks a key event, and links the property to the Google Ads customer; `yandex-metrika` does the analogous thing for Yandex (counter + goal). Analytics Agent's `analyticsToolIds` (default `["google-analytics", "yandex-metrika", "datalens"]`) makes this a list, not a single fixed tool. **Known simplification stated in the Decision Log**: this bundles tracking *setup* into what's nominally Analytics Agent's "read-only" tool call — a deliberate, documented deviation, not an oversight.
  - `datalens` provisions (idempotent by title) an empty DataLens Workbook per project — the container client dashboards will eventually live in. **DataLens-specific auth, and a real gotcha**: the DataLens Public API rejects Yandex Cloud service-account IAM tokens outright (`403 Auth denied`), confirmed with both a hand-signed JWT and an official `yc`-issued token for the same service account — only a genuine *user*-scoped IAM token works. So `lib/tools/datalens.ts` shells out to `yc iam create-token` against a `yc` CLI profile authenticated as a real user (one-time interactive setup: `yc init`, log in with your own Yandex account, select cloud `kalinin-da` / folder `default`), configured via `YC_BINARY_PATH` + `YC_PROFILE` + `DATALENS_ORG_ID` in `.env.local`. **Known limitation**: only the Workbook container is created — building real Connections/Datasets/Charts wired to Direct/Metrika/Ads/GA4 data is a separate, larger piece of work, not started yet.
  - `meta-ads` auth is a System User access token generated once in Business Manager (Business Settings → Users → System Users → Generate Token, with `ads_management`/`ads_read` on the target ad account) — no OAuth refresh flow, same "long-lived token read straight from env" shape as Yandex, configured via `META_ACCESS_TOKEN` + `META_AD_ACCOUNT_ID` (format `act_<id>`) in `.env.local`. Runs at Meta's default **Limited Access** tier, which is enough for a single agency's own ad account — Full Access (higher rate limits, needed only at scale) requires App Review + Business Verification, not done here.
  - `vk-ads` auth is OAuth2 **Client Credentials Grant** (`client_id`/`client_secret` issued once in the account's own "Доступ к API" settings) — manages the agency's own account, no delegated-user step. Unlike Meta, VK tokens expire after ~1 day and are capped at **5 concurrent tokens per client_id** (hit this cap during testing by re-requesting a token per script run instead of caching — `getVkAccessToken()` now caches in-process, same shape as `google-oauth.ts`, specifically to avoid repeating that mistake), configured via `VK_ADS_CLIENT_ID` + `VK_ADS_CLIENT_SECRET` in `.env.local`. **Substantial real gotcha, unlike every other channel**: VK Ads has no concept of an empty campaign container — creating an `AdPlan` requires at least one `AdGroup` referencing a valid `Package` (VK's ad-format template; most `site_conversions` packages returned `invalid_package` for this specific account, `branding_universal_banner` id `3509` is the one that validated), an explicit `budget_limit_day` even though the campaign is immediately blocked, and for site-traffic objectives the target URL must first be registered via `POST /urls.json` (an unregistered URL is rejected with `url_not_checked` — registering the same URL twice is idempotent, VK dedupes server-side, so no separate existence check is needed). `DEFAULT_PACKAGE_ID` in `vk-ads.ts` is hardcoded to what validated for this account; a different client account may need a different package id — flagged as a known limitation, not yet solved generically.
  - **No formal VK Ads agency cabinet**: VK's agency-account status requires spend/case-study history unattainable for a new agency (see Backlog); this integration runs against a regular (non-agency) VK Ads account for now, one account per client rather than a unified multi-client cabinet like Google Ads' MCC.
  - **Per-client accounts, not one global sandbox**: `POST /api/projects` accepts optional `googleAdsCustomerId` / `gtmAccountId` / `gaAccountId` / `yandexClientLogin` / `metaAdAccountId` on `ProjectInput` — when a Project supplies these, PPC/Analytics use the client's own accounts; when it doesn't, everything falls back to the agency's sandbox account (`.env.local`). Verified against two real, independent Google Ads accounts at once: reading real campaigns from a real client account (not the sandbox) via its per-project `customerId`, and a full graph run using explicit per-project ids end to end. **Known Yandex-specific gotcha**: a single Yandex ID can have several linked logins (a "family" of accounts) — the OAuth token must be issued while the correct linked login is active in the browser, or Direct's API rejects every call with error 58 regardless of granted scopes.
  - Every other tool (`seo-service`, `design-tool`, `deployment-tool`) is still a placeholder, so downstream roles still get thin real context about the actual client — expect generic output there until those are wired in too.
- `approve` starts a real **Vercel Workflow DevKit** run (`lib/workflows/execute-project.ts`, package `workflow`, per ADR-0002) instead of blocking the HTTP request — Recovery §3's retry/escalate/block policy (`decideOnFailure`, `packages/workflow-engine/src/recovery-policy.ts`) is now actually wired into live execution, not just proven in isolation by `@ama/reference-scenario`. Real, hard-won finding: `"use workflow"`/`"use step"` functions run in a genuinely **separate execution context** from the rest of this Next.js app — confirmed even under Workflow DevKit's local dev backend ("Local World"), not only in a real distributed Vercel deployment. They cannot read the in-process `ProjectRecord` map (`lib/project-store.ts`) or `MemoryStore` singletons (`lib/singletons.ts`) directly — a direct call from inside a step returns nothing, even though the app's own HTTP routes see the record fine. So every step talks to the app over real HTTP, into small internal-only routes under `app/api/internal/projects/[id]/{graph,run-node,finalize}` that run as ordinary route handlers in the app's own process (the same mechanism `approve`/`reject`/`output` already relied on) — `lib/workflows/execute-project.ts`'s top comment has the full story. Per-tier retry counts (`fast`: 1 retry, `standard`: 3 — `MAX_RETRIES`, exported from `recovery-policy.ts` so both places share the same numbers) map directly onto Workflow's own `stepFn.maxRetries`; a non-retryable `AgentError` throws Workflow's `FatalError` (stops immediately, maps to Recovery's "block"); a retryable one throws a plain `Error` (retried per `maxRetries`, exhaustion maps to "escalate"). `PlanStatus` gained `"failed"`/`"blocked"` terminal values for these two outcomes. Verified end to end via `next dev` (no Vercel account/deployment needed — Workflow's "Local World" backend is zero-config): a full 11-Task happy-path run on both `fast` and `standard` tiers (live progress visible mid-run through repeated `GET` polls, not just a single jump to `"completed"` — this also fixes a real bug where the old synchronous executor only wrote `graphState` back once, at the very end); a genuine real-world retry-then-escalate, hit by accident via an actual Yandex Direct API validation error (`DailyBudget` below the platform's minimum — a real bug, since fixed) that retried 3 times on `standard` tier exactly as `MAX_RETRIES.standard` specifies, then escalated to `PlanStatus: "failed"`. **Not proven**: durability across genuinely separate function invocations in a real Vercel deployment ("Vercel World") — the internal HTTP routes still read/write the same in-process `ProjectRecord` map, so the app's own persistence remains the dev-only `globalThis` convenience described above until the Supabase migration replaces it; what this change does prove is that the workflow/step boundary itself no longer assumes shared process memory, which is the part that would otherwise be impossible to fix later without another rewrite.
- `rework` re-runs only Report Generator against current materials rather than having PM Agent figure out which upstream Tasks the comment actually affects (real FR-5 behavior, not built yet).
